# 选品分级系统 P0 改进交接与验收清单

> 文档性质：供后续 Agent 直接执行的改造任务书
> 本文不包含本轮代码变更；任何实现必须先遵守配套业务规则。
> 必读：`开发部大项目7.13_选品项目全景理解与系统定位.md`、`三赛道独立SAB分级_目标业务规则.md`

## 1. P0 目标

把当前“单次归类、单次评分、全局混排”的分级系统改造成：

```text
统一事实与证据底座
  + 三条独立候选管道
  + 三套独立准入/评分/SAB
  + 三套独立补采与深挖预算
  + 跨赛道汇总决策卡
```

P0 只改进选品分级与决策交付，不负责自动立项、供应商谈判、合规审批或刊登。

实施前必须冻结：

- 当前配置文件；
- 当前 `candidate_packets.jsonl`；

- 当前推荐工作簿；
- 当前 run 元数据和来源审计。

回放必须拆成两组：

1. **严格快照回放**：固定当前 2,000 个候选及其原始事实，不补字段，用于验证三结果模型、状态语义、Gate 分流和“缺销量不强制淘汰”等结构变化；缺新鲜度的候选应进入 `PENDING_DATA`，不得伪造正式趋势等级；
2. **受控增强回放**：保持同一 2,000 个候选集合，仅通过有证据的补采增加新鲜度、款型、相似关系和 VOC 事实；所有新增事实独立版本化，再用新旧引擎分别运行，解释哪些差异来自新事实、哪些来自新规则。

不能更换候选集合后宣称规则改善，也不能把补采事实偷偷写回旧快照。

## 3. 非目标

P0 不要求：

- 直接生成可刊登商品；
- 填满 Canonical 152 键；
- 自动创建正式 `project_id/spu_id/sku_id`；
- 自动批准改款、新品或采购；
- 自动给出侵权、合规最终结论；
- 建立完整 ERP/PLM/OMS 回流；
- 用 LLM 替代确定性评分。

## 4. P0 工作包一：统一术语和结果模型

### 4.1 目标

将“赛道”和“开发方式”拆开，允许一个候选产生多条赛道结果。

### 4.2 必须交付

- 赛道键：`trend_new`、`hit_improvement`、`long_tail_direct`；
- 开发方式字段：`recommended_development_mode`；
- 赛道准入状态：`ELIGIBLE/PENDING_DATA/REJECTED`；
- 结果唯一键：`run_id + subject_type + subject_id + track_id`；
- 每个原始候选每个 run 恰好生成三条候选级结果；趋势机会簇可额外生成簇级结果，候选级记录引用其簇版本；
- 每条结果独立保存 grade、score、components、evidence、missing、risk 和 next actions；
- `balanced` 不再作为可产生业务等级的第四赛道。

### 4.3 兼容要求

- 旧 `candidate_id`、证据 ID 和 Canonical 152 键不得失去关联；
- 旧 run 可继续读取；
- 新旧规则版本必须明确区分；
- 如果保留旧 `track` 字段，必须标注它属于旧版本，不能与新结果混用。

## 5. P0 工作包二：扩展新款型与来源角色数据契约

### 5.1 当前缺口

`CandidateDataPacket` 没有正式的新鲜度字段；独立站只作为普通前端来源进入统一评分。

### 5.2 建议新增的事实字段

字段名可以根据现有契约规范调整，但语义必须覆盖：

- `listed_at`：来源明确提供的上架/首次可售时间；
- `first_seen_at`：系统首次观察到该商品的时间；
- `last_seen_at`：最近一次仍存在的时间；
- `new_arrival_flag`：页面明确新品标记；
- `collection_name/season`：系列或发布季；
- `earliest_review_at`：最早可验证评论时间；
- `earliest_content_at`：最早关联内容时间；
- `freshness_status`：confirmed/inferred/unknown/old；
- `freshness_evidence_refs`；
- `source_roles[]`：discovery/content/transaction/voc/supply/owned_feedback，可多选且逐项绑定依据；
- `style_attributes`：廓形、材质、颜色、图案、长度、结构、场景；
- `observation_time` 与字段级采集时间。

### 5.3 红线

- 不得把采集时间冒充上架时间；
- 不得从商品 ID 大小直接推断上架时间，除非来源规则有证据；
- 不得因上架时间缺失伪造日期；
- 不得把标题中的普通单词 `new` 直接当新品事实；
- 所有推断型新鲜度必须带置信度和证据。
- `first_seen_at` 只表示系统首次观察；只有存在更早的连续监测快照并能证明此前不存在时，才可作为近期推出的辅助证据；
- 页面/SKU 新鲜度和市场款型新颖度必须分字段保存，不能互相替代。

## 6. P0 工作包三：建立机会簇和三种相似关系

### 6.1 目标

让独立站的款型观察可以与 TikTok、SHEIN、Amazon 或其他站点的类似款形成趋势机会，而不是要求同一个商品 ID 跨平台出现。

### 6.2 必须区分

- `same_product`：同商品/同货源；
- `same_style`：结构和款式高度相似；
- `same_trend`：共享趋势元素，但不是同款。

### 6.3 证据

召回和判断至少考虑：

- 图片；
- 标题；
- 类目；
- 款型属性；
- 价格和品牌边界；
- 上新/首次发现时间；
- TikTok 内容元素与发布时间。

### 6.4 人工边界

- 低置信度关系必须进入人工复核队列；
- 标题词表只可用于召回；
- 未经确认不得把 `same_style/same_trend` 写成同商品；
- 聚类应保留成员和每条关系的证据，不能只输出一个无来源的趋势词。
- 机会簇必须版本化，保存成员变更、合并/拆分和 lineage；
- 在业务标注的相似样本与阈值未确认前，只能实现召回、证据和人工复核框架，不得把未校准相似分数用于正式等级。

## 7. P0 工作包四：实现三条独立管道

### 7.1 趋势新品管道

必须做到：

- 以新款型证据为准入核心；
- 同时验证“近期推出”和“相对目标市场历史款型的新颖度”；
- 不设置销量、评论数、GMV、收藏数、达人量和增长率硬门槛；
- 无销量不触发强制 C；
- 多平台相似和 TikTok 信号只加权；
- 单源早期新品可以进入 B；
- 缺任一类新款证据时进入 `PENDING_DATA`；确认是旧商品或旧款型时才 `REJECTED`；
- 输出趋势专属补采任务和专属 L2/L3 队列。

### 7.2 爆款改款管道

必须做到：

- 联合验证适量销量/需求、低评分、多个负面聚类；
- 销量按平台/类目/窗口相对分布配置，不使用一个跨平台绝对值；
- 评论聚类保留频次、占比、严重度、变体、时间和证据；
- 区分产品可解决问题与物流/客服/误购问题；
- 缺评论全文时进入 `PENDING_DATA`，不能仅凭评分生成高等级改款结论。

### 7.3 长尾直接选品管道

必须做到：

- 以稳定需求、竞争可切入和直接承接可行性为主；
- 不再用基础关键词代表整个长尾赛道；
- 不把未命中前两条赛道的商品自动塞入本赛道；
- 供应链事实不足时明确补采，不以猜测填充。

## 8. P0 工作包五：重构 Gate 和预算

### 8.1 当前问题

- `run_l1` 使用的需求字段与 `score_demand` 不一致；
- L2/L3 只按全局分数截断；
- 不同赛道缺失同一字段时受到相同处理。

### 8.2 必须交付

- 每条赛道独立的 L1/L2/L3 配置；
- 每条赛道独立的 `eligible_grades` 与 `max_candidates`；
- 每条赛道独立的必备字段和缺失动作；
- 评分器与 Gate 共享同一份信号注册表，避免同一字段“评分算需求、Gate 不算需求”；
- 趋势新品缺交易数据时不降级；
- 改款缺 VOC 时进入待补；
- 长尾缺稳定需求时进入待补或拒绝；
- 每个 Gate 输出明确的进入、待补和拒绝原因。

内部状态不得重新压成一个 C：`PENDING_DATA` 与 `REJECTED` 的 `grade` 均为空；旧表兼容只能附加 `legacy_grade=C`。

### 8.3 名额原则

三个赛道不得默认共享“全局 L2 前 40、L3 前 10”。建议配置为：

```text
l2.max_candidates_by_track
l3.max_candidates_by_track
```

具体数量由业务负责人确认。Agent 不得自行平均分配，也不得根据旧全局排名自动挪用。

## 9. P0 工作包六：评分与等级配置

### 9.1 配置原则

- 三份赛道配置相互独立；
- 允许共享底层指标函数，但不共享准入和总分公式；
- 阈值通过各赛道金标和历史回放校准；
- 所有参数有版本、批准人、生效时间和变更原因；
- LLM 可以提出 `grade_challenge`，但不能直接写回正式等级。

### 9.2 不能沿用的硬规则

趋势新品不能继续使用：

- `growth >= 30%` 或畅销榜作为唯一准入；
- S 必须同一商品有两个来源；
- 缺交易型 demand signal 强制 C。

趋势 S 的多源证据应允许来自“同一机会簇中的多个独立款型观察/内容信号”，而不是要求同一商品 ID 跨源合并。

爆款改款不能继续只使用：

- `rating <= 4.30 && review_count >= 10`。

它必须增加真实需求基础和负面聚类丰富度/可改性判断。

## 10. P0 工作包七：重做推荐交付

### 10.1 最低页签

- `趋势新品_SAB`
- `爆款改款_SAB`
- `长尾直接选品_SAB`
- `跨赛道汇总`
- `待补数据`
- `未准入与淘汰依据`
- `机会簇与跨平台相似`
- `评分明细`
- `证据索引`
- `数据源覆盖与角色`
- `规则版本与运行记录`
- 现有 152 键页签

### 10.2 每张 S/A/B 表必须显示

- track-specific rank；
- grade；
- candidate/cluster ID；
- 来源角色和平台；
- 准入理由；
- 本赛道评分明细；
- 新鲜度/需求/VOC 等核心证据；
- 置信度；
- 风险；
- 缺失字段；
- 下一步；
- evidence refs；
- 推荐开发方式。

### 10.3 跨赛道汇总

必须能展示同一候选在三条赛道中的不同结果，不能只保留一个主赛道覆盖其他结果。

## 11. P0 工作包八：测试、回放与金标

### 11.1 单元/规则测试

至少覆盖：

1. 新款型有明确新品证据、没有销量，仍可进入趋势评分；
2. 新款型只有单站，仍可进入趋势 B 观察；
3. 多平台类似款提高趋势分，但移除相似证据后仍不改变其准入状态；
4. 旧款即使增长高，也不能自动成为趋势新品；
5. 有销量、低评分、多负面聚类的商品进入改款评分；
6. 只有低评分没有销量，不进入改款；
7. 有销量、低评分但无评论聚类，进入 `PENDING_DATA`；
8. 负面问题只有物流/客服原因，不得给高改款等级；
9. 未命中前两条赛道不等于自动进入长尾；
10. 每个候选每个 run 恰好保存三条候选级 TrackEvaluation，簇级结果另存；
11. 三条赛道 L2/L3 名额互不挤占；
12. 所有分数和准入理由有证据；
13. 同一输入重复计算结果一致。

### 11.2 基线回放

分别执行“严格快照回放”和“受控增强回放”，至少对比：

- 三条赛道的准入、待补、拒绝和 S/A/B 分布；
- 来源角色分布；
- 独立站进入趋势准入和待补的比例；
- 每条赛道 L2/L3 平台分布；
- 与旧结果的候选增减及原因；
- 每条规则变化的影响；
- 典型边界商品。

严格快照回放验证结构和缺失策略，不能要求缺新鲜度的独立站候选直接产生趋势 S/A/B；受控增强回放才用于验证正式趋势等级和来源分布。

不得以“独立站 S/A/B 数量变多”单独证明改进成功。正确性必须通过新鲜度证据、跨平台关系和人工金标确认。

### 11.3 人工金标

业务人员需要分别提供：

- 每条赛道的优秀、失败和边界商品；
- 正确准入状态；
- 正确 S/A/B；
- 错误原因；
- 多平台相似对；
- 可改与不可改的 VOC 样本。

首版目标沿用 XMind：人工金标一致率 ≥85%，重复计算一致率 100%，解释与证据覆盖率 100%。

## 12. Given/When/Then 验收场景

### 场景一：趋势新品无销量

- Given：商品同时具备可信近期推出证据和款型新颖度证据，但没有销量、评论或增长率；
- When：运行趋势新品管道；
- Then：准入状态必须为 `ELIGIBLE` 并进入趋势 S/A/B；不得因缺交易数据降为 C 或待补，且必须显示两类新款证据。

### 场景二：多平台类似款加权

- Given：一个新品款型在两个独立站和 TikTok 内容中出现相似元素；
- When：建立机会簇并运行趋势评分；
- Then：跨平台共振提高分数和置信度，但关系必须标为同款式/同趋势，不能声称同商品。

### 场景三：改款三项联合准入

- Given：商品有适量销量、评分显著偏低、多个高频可改负面聚类；
- When：运行爆款改款管道；
- Then：进入改款 S/A/B，并完整展示三类准入证据和改良方向。

### 场景四：低评分小样本

- Given：商品评分低但销量和评论样本很少；
- When：运行爆款改款管道；
- Then：不得仅凭低评分进入高等级，应待补或拒绝。

### 场景五：独立站来源角色

- Given：独立站商品缺平台成交字段，但有新品和款型证据；
- When：运行全系统；
- Then：它按发现源参与趋势判断，不能被公共 L1 需求 Gate 自动淘汰。

### 场景六：三赛道独立预算

- Given：交易平台候选在长尾赛道分数很高；
- When：选择趋势赛道 L2/L3 候选；
- Then：它不得挤占趋势新品的专属名额，除非它本身也通过趋势准入。

### 场景七：首次采集不等于新品

- Given：系统第一次采到某商品，但没有更早快照、上架时间或市场款型新颖度证据；
- When：运行趋势新品管道；
- Then：结果必须是 `PENDING_DATA`，不能仅凭 `first_seen_at` 进入趋势 S/A/B。

### 场景八：旧款已确认

- Given：历史款型库或人工复核确认该商品属于旧款型；
- When：运行趋势新品管道；
- Then：结果必须是 `REJECTED`，并绑定旧款证据；销量增长不能覆盖该结论。

## 13. P0 量化验收标准

### 13.1 必须达到

- 三条赛道均有独立运行记录和 S/A/B 结果结构；
- 每个候选每个 run 的三条候选级 TrackEvaluation 完整率 = 100%；
- 趋势新品因缺销量被强制淘汰的数量 = 0；
- 趋势 S/A/B 新鲜度证据覆盖率 = 100%；
- 改款 S/A/B 的需求、低评分、负面聚类证据覆盖率 = 100%；
- 独立站候选按来源角色完成趋势准入判断的覆盖率 = 100%；
- 三赛道评分明细和证据解释覆盖率 = 100%；
- 相同输入重复计算一致率 = 100%；
- 低置信度相似关系送人工复核率 = 100%；
- 人工金标一致率 ≥85%；
- 未确认数据被伪造或均值填充的次数 = 0；
- LLM 未经人审直接改变正式等级的次数 = 0。

### 13.2 需要观察，不应硬设配额

- 独立站最终 S/A/B 数量；
- 每条赛道 S/A/B 的绝对比例；
- 各平台进入 S/A/B 的占比；
- 多平台机会簇数量。

这些是规则结果，不应为了“看起来均衡”强行设定平台配额。应通过金标和真实经营回流判断是否合理。

## 14. 推荐实施顺序

1. 冻结旧 run 和建立前后对照脚本；
2. 并行启动业务确认：三个赛道正式名称、金标、阈值、名额和风险红线；该步骤不阻塞后续基础骨架，但阻塞正式生产等级启用；
3. 扩展数据契约：商品新鲜度、款型新颖度、多值来源角色、款型属性；
4. 修复评分器与 Gate 的需求信号口径冲突；
5. 建立 TrackEvaluation 一对多结果模型；
6. 拆出三套准入、评分、L1/L2/L3 和预算配置槽；未批准参数保持禁用或校准状态；

## 18. Definition of Done

P0 只有同时满足以下条件才算完成：

- 业务负责人确认三条赛道定义和待校准参数；
- 三条赛道可独立运行并各自产出 S/A/B；
- 趋势新品规则不再以高销量或增长率作为准入；
- 改款规则落实三项联合准入；
- 独立站不再被结构性淘汰；
- 三套 Gate 和预算生效；
- 新旧基线回放完整；
- 自动化测试、证据审计和确定性检查通过；
- 金标一致率达到目标；
- 款型历史库/回看窗口、销量/评分/VOC 阈值、相似阈值、风险红线和三赛道名额均有业务批准记录；
- 推荐表能向业务解释每条赛道的结果；
- 未扩张到自动立项、合规或刊登范围。
