# 分层分析系统组任务书

---

## 1. 组目标

建立可持续运行的选品分析系统，而不是一次性报告提示词。

系统必须能消费：

1. 插件 HTTP MCP 数据。
2. 前端采集数据。
3. 站外趋势轻量数据。
4. 自有/供应链人工输入。

系统必须输出：

1. L1/L2/L3 分层结果。
2. Priority Score。
3. S/A/B/C 分级。
4. 推荐理由、风险理由、证据。
5. XLSX 推荐表。

核心原则：

1. L1 全量粗筛，低成本。
2. L2 入围精调研，只对候选做差评和改良分析。
3. L3 终选多平台比对，只对终选款做高成本分析。
4. 每个结论必须绑定证据。
5. 大模型可以设计评分理由和分析结构，但不能编造事实数值。
6. 前端采集与分层分析的先后顺序待定：默认按 Gate 控制高成本采集，但也允许先做受控全量采集，再统一分析和分级。

---

## 2. 推荐分工

四人总配置下，本组由 D1 一人负责：

| 人 | 负责 | 重点 |
|---|---|---|
| D1 | 分层分析架构、候选数据包、Gate、成本控制、证据模型、缺字段策略、PScore、差评聚类、多平台比对、XLSX 输出、样例报告 | 系统结构、接口、可追溯、业务评分、报告可读性、LLM 输出约束 |

主线程不要再配置固定“报告员工”或第二名分析员工。XLSX 样式、字段字典、QA checklist 可由 GPT 轻量任务池基于 D1 的真实 schema 生成。

---

## 3. 分层分析不是 GPT 一次打分

禁止流程：

```text
把所有数据都丢给 GPT -> 让 GPT 直接给推荐表
```

正确流程：

```text
L1 全量粗筛：插件 MCP 批量量价 + 前端基础字段 + 轻量趋势
-> Gate 1：筛掉大部分候选
-> L2 入围精调研：详情、差评全文、Q&A、单平台竞品评分卡
-> Gate 2：保留可改良、可供应、风险可控的候选
-> L3 终选多平台比对：Amazon/TikTok Shop/Shein/独立站同款、价格、痛点、趋势
-> 人审/立项
```

待定决策：

```text
方案 A：先 L1 粗筛，再触发 L2/L3 前端补采，成本最低。
方案 B：先对目标站点做受控全量前端采集，再统一进入 L1/L2/L3 分析，数据更完整但成本更高。
```

第 1 天必须由主线程、C1、D1 决定本周采用 A、B 或混合方案，并写入 `collection_mode`。

## 5. 统一输入接口

### 5.1 SourceEnvelope

所有数据源都必须交付统一 envelope。插件 MCP 和前端采集的 source_type 不同，但结构一致。

```json
{
  "envelope_id": "source_helium10_B0XXXX_20260626",
  "source_id": "helium10",
  "source_type": "plugin",
  "market": "US",
  "collection_mode": "layered",
  "layer_hint": "L1",
  "layer": "L1",
  "schema_version": "source.envelope.v1",
  "collected_at": "2026-06-26T00:00:00Z",
  "collector_version": "0.1.0",
  "quality_status": "VALID",
  "records": [],
  "errors": [],
  "artifact_paths": {}
}
```

字段要求：

| 字段 | 要求 |
|---|---|
| `source_id` | 数据源唯一 ID，如 `helium10`、`kalodata`、`shein_frontend`、`tiktok_shop_frontend` |
| `source_type` | `plugin` / `frontend` / `trend` / `owned` / `compliance` |
| `market` | P0 固定 `US`，不得混入其他市场 |
| `collection_mode` | `layered` / `full_then_analyze` / `mixed`，说明数据是按层触发还是先采后分 |
| `layer_hint` | 该 envelope 主要服务的层级：`L1` / `L2` / `L3`；全量采集时可标记预计用途 |
| `layer` | 兼容旧字段，含义同 `layer_hint`；新实现优先使用 `layer_hint` |
| `quality_status` | `VALID` / `PARTIAL_SOURCE_MISSING` / `PARSE_FAILED` / `ACCESS_BLOCKED` 等 |
| `records` | 标准化记录 |
| `artifact_paths` | raw、normalized、workbook、log 等路径 |

### 5.2 EvidenceRef

所有事实字段必须能追溯证据。

```json
{
  "evidence_id": "ev_helium10_B0XXXX_sales_001",
  "source_id": "helium10",
  "source_type": "plugin",
  "tool_or_adapter": "helium10_product_xray",
  "field_path": "market_metrics.estimated_monthly_sales",
  "artifact_uri": "data/raw/mcp_sources/helium10/run_20260626_001/product_xray.json",
  "artifact_path": "data/raw/mcp_sources/helium10/run_20260626_001/product_xray.json",
  "observed_at": "2026-06-26T00:00:00Z",
  "confidence": "high"
}
```

EvidenceRef 必须绑定到具体字段，而不是只绑定到“某个数据源”。无法绑定证据的结论不能进入推荐总表。

### 5.3 CandidateDataPacket

每个候选进入分析时，不直接读原始数据源，而是读候选数据包。

```json
{
  "candidate_id": "cand_B0XXXX_US",
  "market": "US",
  "primary_product_id": "B0XXXX",
  "canonical_url": "https://www.amazon.com/dp/B0XXXX",
  "source_refs": [
    {
      "source_id": "helium10",
      "envelope_id": "source_helium10_B0XXXX_20260626"
    },
    {
      "source_id": "shein_frontend",
      "envelope_id": "frontend_shein_123_20260626"
    }
  ],
  "basic_facts": {
    "title": "",
    "brand": "",
    "category_path": [],
    "images": [],
    "price": null,
    "currency": "USD",
    "rating": null,
    "review_count": null
  },
  "market_metrics": {
    "estimated_monthly_sales": null,
    "estimated_monthly_revenue": null,
    "bsr": null,
    "search_volume": null,
    "trend_signals": []
  },
  "competition_metrics": {
    "seller_count": null,
    "review_threshold": null,
    "price_band": null,
    "brand_concentration": null
  },
  "product_opportunity": {
    "negative_review_clusters": [],
    "improvement_points": [],
    "differentiation_options": []
  },
  "cross_platform": {
    "matched_products": [],
    "platform_price_comparison": [],
    "same_style_signals": []
  },
  "owned_supply_inputs": {
    "target_cost": null,
    "moq": null,
    "lead_time_days": null,
    "fabric_capability": [],
    "compliance_notes": []
  },
  "missing_fields": [],
  "field_issues": [],
  "evidence_pack": [],
  "quality_status": "VALID"
}
```

硬性规则：

1. `CandidateDataPacket` 是分析唯一输入。
2. 缺字段必须写入 `missing_fields`。
3. 不确定字段必须写入 `field_issues` 或降低 confidence。
4. LLM 不允许把 `null` 补成看似合理的数值。
5. Google Trends、AnySearch 等只能作为趋势信号，不能当销量或收入事实。

### 6.2 Grade 定义

| 分级 | 含义 | 后续动作 |
|---|---|---|
| S | 高优先级，值得进入立项讨论 | L2/L3 补齐后人审 |

## 7. L1/L2/L3 输入输出

### 7.1 L1 粗筛

| 项 | 内容 |
|---|---|
| 对象 | 全量候选 |
| 输入 | 插件 MCP 批量量价、榜单、基础前台字段、轻量趋势 |
| 不做 | 差评全文、大量图片、多平台深比 |
| 输出 | 初始 PScore、三赛道标签、S/A/B/C 初排、L2 需要补采字段 |

L1 必填字段建议：

1. `candidate_id`
2. `canonical_url`
3. `title`
4. `market`
5. `category_path` 或来源榜单上下文
6. 至少一个需求信号：销量估算、BSR、榜单排名、搜索量、趋势信号之一
7. 至少一个竞争信号：评论数、评分、卖家数、价格带之一

L1 Gate v0：

| 条件 | 动作 |
|---|---|
| 无产品链接或无产品 ID | 阻断 |
| 无任何需求信号 | 降为 C 或进入补采 |
| 价格/币种缺失 | 可继续，但标记 L2 补采 |
| 评论数极高且无差异化信号 | 降级 |
| 数据源质量状态非 VALID | 降低 confidence 或阻断 |

### 7.2 L2 精调研

| 项 | 内容 |
|---|---|
| 对象 | L1 入围 S/A/B |
| 输入 | 商品详情、评论/差评、Q&A、单平台竞品 |
| 处理 | 差评聚类、改良点、单平台评分卡 |
| 输出 | 改款建议、风险理由、L2 分级、L3 是否需要多平台比对 |

L2 必填字段建议：

1. 至少 20 条评论或明确的评论缺失原因。
2. 至少 5 条低分评论，或记录低分评论不可得。
3. 主图和关键属性。
4. 价格、评分、评论数。
5. 已识别的主要痛点或“痛点不足”的结论。

差评聚类输出必须是结构化 JSON：

```json
{
  "clusters": [
    {
      "cluster_name": "尺码偏小",
      "frequency_hint": "high",
      "representative_reviews": [],
      "improvement_opportunity": "版型和尺码表优化",
      "risk_if_unfixed": "退货率可能偏高",
      "evidence_refs": []
    }
  ]
}
```

### 7.3 L3 多平台比对

| 项 | 内容 |
|---|---|
| 对象 | L2 终选 S/A |
| 输入 | Amazon/TikTok Shop/Shein/独立站同款候选、价格、竞争、痛点 |
| 处理 | 同货源/同款式/同微趋势分组 |
| 输出 | 平台优先级、红海程度、差异化空间、终选建议 |

L3 输出必须回答：

1. 该候选优先在哪个平台推进。
2. 是否是同款红海。
3. 是否有可解释的差异化空间。
4. 供应链输入是否支持改款。
5. 需要补充哪些人工判断。

## 8. PScore v0

初版评分框架：

| 维度 | 建议权重 | 说明 |
|---|---:|---|
| 市场需求 | 25 | 搜索量、销量估算、销售额估算、BSR、趋势上升 |
| 竞争可突破 | 20 | 集中度、Review 门槛、卖家数量、价格带 |
| 产品机会 | 20 | 差评痛点、改良空间、差异化元素 |
| 自有/供应链 | 20 | 毛利、MOQ、生产周期、面料能力 |
| 风险 | -15 | 侵权、合规、退货、季节窗口、数据可信度 |

评分规则：

1. PScore v0 是可运行框架，业务后续可调权。
2. 模型可以建议调权，但不能擅自把建议权重当最终业务事实。
3. 每个 component 必须给 evidence_refs。
4. 缺字段时，不得给满分；必须降置信度或进入 `required_next_data`。
5. 风险维度可以扣分，但扣分理由必须绑定证据或明确为人工待确认。

三赛道标签建议：

| 标签 | 含义 |
|---|---|
| `基础常青款` | 需求稳定、趋势不剧烈，适合供应链稳定推进 |
| `趋势上升款` | 趋势信号明显上升，但窗口期和库存风险更高 |
| `痛点改良款` | 差评中存在可改良空间，适合通过产品优化切入 |
| `价格带机会款` | 目标价格带竞争结构较好 |
| `观察款` | 数据不足或风险未明，暂不立项 |

## 9. LLM 使用边界

允许 LLM 做：

1. 总结差评主题。
2. 把字段转成业务语言。
3. 设计评分理由。
4. 提出调权建议。
5. 生成推荐理由和风险理由。
6. 对同款/同趋势候选做结构化比较。

禁止 LLM 做：

1. 编造销量、搜索量、销售额、MOQ、毛利、成本。
2. 把 Google Trends 指数解释成销量。
3. 把缺字段补成行业均值。
4. 不带证据地输出推荐理由。
5. 把“页面没采到”写成“没有该问题”。

所有 LLM prompt 都必须要求 JSON 输出，并在 schema 中保留：

1. `evidence_refs`
2. `confidence`
3. `missing_fields`
4. `assumptions`
5. `blocked_reasons`


1. 无产品链接。
2. 无证据来源。
3. 市场混乱。
4. 明文 token/cookie 泄漏。
5. 推荐理由缺 evidence_refs。

## 13. 成本控制策略

| 阶段 | 控制方式 |
|---|---|
| L1 | 批量低成本字段，不采评论全文，不做多平台 |
| L2 | 只对 L1 入围款采评论和详情补全 |
| L3 | 只对 L2 终选款做多平台同款和深度对比 |
| LLM | prompt 输入只放必要字段和证据摘要，不塞 raw HTML |
| XLSX | 只读 AnalysisResult，不触发新采集 |

如果第 1 天选择“先全量前端采集”方案，成本控制不再依赖采集顺序，而依赖采集预算、字段范围、页数上限、站点限流和 evidence 分层标记。分析系统仍然必须用 L1/L2/L3 Gate 控制后续 LLM 和深度比对成本。

任何任务如果要扩大采集范围，必须说明：

1. 为什么需要。
2. 服务哪个 Gate。
3. 预计新增成本。
4. 输出字段如何进入 CandidateDataPacket。

---

## 14. 验收标准

P0 分层分析系统通过标准：

1. 能消费插件 MCP 和前端采集的真实样例。
2. 能从多个 SourceEnvelope 生成 CandidateDataPacket。
3. L1 不调用高成本评论/多平台分析。
4. L2 只对入围款做差评聚类。
5. L3 只对终选款做多平台比对。
6. 每条推荐理由有 evidence_refs。
7. 缺字段不会被模型脑补。
8. 能生成业务可读 XLSX。
9. 输出包含 S/A/B/C 分级和 PScore。
10. 阻断项能被明确写入 blocked_reasons。

阻断项：

1. 无 evidence_refs 的推荐理由进入 XLSX。
2. LLM 编造数值。
3. Google Trends 被当作销量。
4. 缺字段被隐藏。
5. 原始 token/cookie/Auth-Token 出现在报告或日志里。

