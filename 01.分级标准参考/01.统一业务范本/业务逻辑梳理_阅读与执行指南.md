# 业务逻辑梳理：阅读与执行指南

本文是对当前目录内业务逻辑文档的总览梳理，目标是回答三个问题：

1. 你需要先了解什么。
2. 这套业务内容是怎么运转的。
3. 真正执行落地时按什么顺序做。

---

## 1. 这批文档到底在讲什么

这套资料定义的是一个「跨境多平台铺货运营底座」。

一句话说：把选品、铺货、刊登、内容、维护、风控、复制/退出这些跨境运营动作，沉淀成统一的数据模型、规则引擎、字段映射、Agent 执行流和开发工单，让多平台铺货从人工经验活变成可复制的系统能力。

北极星指标是：每万条 Listing 所需人工工时下降。

最终想达到的状态是：多个 Agent 管理大量平台、店铺、产品和 Listing，人工主要负责规则赋值、异常审核、战略判断，而不是一条条手工铺货和维护。

## 2. 你最需要先掌握的 10 个核心概念

### 2.1 三个系统边界

| 系统 | 你要理解成什么 | 负责什么 | 不负责什么 |
|---|---|---|---|
| 数据中台 | 唯一事实源 | 主数据、决策数据、规则、映射配置、成本利润 | 不执行刊登动作，不做 LLM 推理 |
| ERP | 单据系统 | 采购、库存实物数、订单、履约、对账 | 不再作为商品主数据源 |
| 智能平台 | Agent 运行时 | Agent、Workflow、Skill、执行日志、编排器 | 不持有主数据权威，不绕过中台写主数据 |

最重要的结论：商品、店铺、规则、映射、成本利润这些权威信息都收敛到数据中台；ERP 退回进销存单据；智能平台只负责调度和执行。

### 2.2 三条铁律

| 铁律 | 含义 |
|---|---|
| 主数据单向收敛 | 主数据写入只走中台权威接口，其他系统只读或订阅 |
| 确定性操作禁用 LLM 决策 | 改价、改库存、上下架、字段直填等数值动作必须由规则/映射决定 |
| SOP/规则是单一事实源 | 规则和流程沉在中台，Agent 只执行，不私自写死业务逻辑 |

### 2.3 业务价值链

完整链路是：

选品情报 → Priority Score 打分 → 商品 S/A/B/C 分级 → 店货匹配 → CanonicalProduct 抽取 → 类目字段映射 → 内容生产 → 风险分级发布 → 执行通道刊登 → 在线维护 → 店铺安全风控 → 双利润核算 → 加码/复制/退出。

### 2.4 五层架构

| 层级 | 作用 |
|---|---|
| L1 战略决策层 | Project、进入/复制/退出、双利润 |
| L2 运营计划层 | 店铺画像、商品分级、铺货计划、活动广告计划 |
| L3 执行内核层 | Canonical Model、6 通用 Skill、映射引擎、风险发布引擎 |
| L4 智能编排层 | 主干 Agent、子 Agent、评审 Agent、编排器 |
| L5 数据与知识底座 | 数据中台、知识库、ERP 单据 |

### 2.5 CanonicalProduct

CanonicalProduct 是跨平台复用铺货的核心。

它把不同平台的字段差异收敛为平台无关的标准商品字段。附录 E 将 Amazon、Temu、Shein 三个平台女装类目共 508 个平台字段映射成 152 个 Canonical 键。

这件事的意义是：以后加平台、加类目，尽量改配置和映射，不改业务代码。

### 2.6 变与不变

| 类型 | 例子 | 放哪里 |
|---|---|---|
| 不变 | 标题基底、描述、品牌、材质、款式、包装尺寸 | CanonicalProduct |
| 变 | 价格、库存、站点、店铺、促销、部分平台字段 | SiteOffer / 平台扩展属性 |

这是全套架构的命门：把平台差异、类目差异、店铺差异都配置化；把通用操作沉为内核。

### 2.7 统一分级口径

| 对象 | 分级 |
|---|---|
| 商品 | S/A/B/C，来自 Priority Score 分箱 |
| 店铺 | 三个正交维度：安全等级、刊登优先级、定位标签 |
| 刊登级别 | L1-L4，表示内容投入档 |
| 发布风险 | 自动 / 人工 / 禁发，由操作性质、内容质量、店铺成熟度决定 |
| 内容质量 | P0 禁发、P1 人审、P2 可自动但建议优化 |

注意：刊登级别 L1-L4 和发布风险不是一回事，不能混用。

### 2.8 6 个通用 Skill

智能平台最终要沉淀 6 个通用操作：

| Skill | 含义 |
|---|---|
| SubmitListing | 刊登 |
| UpdatePrice | 改价 |
| UpdateInventory | 改库存 |
| Delist-Relist | 下架/重上架 |
| SyncStatus | 同步状态 |
| UpdateDetail | 改详情 |

执行通道优先级：API > 批量上传表 > RPA/紫鸟。

### 2.9 规则引擎

规则统一进入 `t_rule`，按 domain 分区：

| domain | 解决什么 |
|---|---|
| priority_score | 选品打分和商品 S/A/B/C |
| publish_risk | 发布风险判级 |
| maintain | 在线维护，比如改价、补货、下架 |
| shop_safety | 店铺安全红线和降级 |
| replicate_exit | 加码、复制、退出 |
| content_quality | 内容 P0/P1/P2 质检 |
| field_required | 字段必填和映射校验 |

所有 `draft` 规则不参与自动执行，只有 `active` 规则能进入自动决策。

### 2.10 P0 关键路径

P0 地基必须先做，顺序是：

M10 主数据底座 → M2 Canonical+映射引擎 → M3 6 通用 Skill+执行通道 → M4 风险分级发布 → M9 多 Agent 编排器。

P0 里程碑是：能把 1 个 CanonicalProduct 自动复用刊登到第 2/第 3 个平台。

## 3. 内容是怎么做的：端到端业务流

### 3.1 选品进入

流程：

1. 从趋势款、爆款款、长尾款三条赛道收集候选。
2. 进入 Priority Score 统一公式。
3. 生成商品 S/A/B/C 分级。
4. 高分商品进入 Project，分配预算和铺货优先级。

你要补充确认的点：

| 待确认 | 用途 |
|---|---|
| 不同赛道权重 | 趋势店、清货店等策略不同 |
| S/A/B/C 分数阈值 | 决定商品投入级别 |
| 情报源列表 | Google Trends、TikTok、Amazon BSR、Shein 榜等 |
| 风险扣分标准 | 侵权、退货、尺码、季节窗口等 |

### 3.2 标准铺货

流程：

1. 选择商品和目标店铺。
2. 从中台抽取 CanonicalProduct。
3. 读取目标平台、类目、店铺配置。
4. 通过 `t_category_mapping` 映射成平台字段。
5. 通过 `t_value_dict` 做枚举转换。
6. 缺必填字段则阻断并回写缺口。
7. 进入风险分级发布。
8. 自动或人工确认后，通过 SubmitListing 发布。
9. 结果回写中台 Listing 镜像。

关键点：平台字段不能硬编码，必须读 active 映射配置。

### 3.3 跨平台复用铺货

这是当前 P0 样板流程。

流程：

1. 选择一个成熟 Listing。
2. 抽取或反推 CanonicalProduct。
3. 选择目标平台和目标店铺。
4. 用 20 个三平台共有 Canonical 键先跑最小可发布集。
5. 按目标平台补独有字段。
6. 换图、换文案、规避重复。
7. 风险判级后发布。
8. 回写中台。

三平台共有 20 键包括：标题、描述、品牌、卖家 SKU、产地、附图、库存、售价、材质、面料克重、面料弹性、风格、领型、袖长、门襟、版型、护理、细节、包装尺寸、包装重量。

### 3.4 内容生产

流程：

1. 从中台读取商品主档。
2. 读取店铺定位：货盘定位 + 内容调性。
3. 结合平台规则和关键词。
4. 生成标题、卖点、描述、图片或视频。
5. 规则校验和内容质检。
6. P0 禁发，P1 人审，P2 可自动发布但记录建议。
7. 内容资产多版本入库，表现数据回流优化。

关键点：内容可以用 LLM/AI，但必须经过规则校验和质量分级；确定性字段不能由 LLM 编。

### 3.5 在线维护

流程：

1. 监控库存、价格、ACOS、滞销周期等指标。
2. 命中 `t_rule(domain=maintain)` 阈值。
3. 触发改价、改库存、上下架等动作。
4. 数值由规则算，不让 LLM 决定。
5. 通过 6 通用 Skill 执行。
6. 结果回写中台并校验。

你要补充确认的点：

| 待确认 | 例子 |
|---|---|
| 库存可售天数阈值 | 小于 X 天补货或下架 |
| 价格竞争阈值 | 恶化超过 Y% 改价 |
| 广告阈值 | ACOS 超过 Z 降出价 |
| 滞销周期 | N 周期后转清货或降级 |

### 3.6 店铺安全风控

流程：

1. 平台 KPI 回传。
2. 按平台读取红线配置。
3. 命中红线后自动降级店铺安全等级。
4. 限制刊登优先级。
5. 收缩铺货计划。
6. 通知到人。

关键点：不同平台 KPI 不同，必须配置化，不允许把 Amazon 的红线硬套到所有平台。

### 3.7 复制/退出决策

流程：

1. 周期性结算销售、广告、仓储、退货、平台费等数据。
2. 同时计算边际贡献利润和全成本利润。
3. 根据决策门判断 SKU 加码、品类复制、平台复制、国家复制或停止复制。
4. 更新 Project 阶段和预算。

你要补充确认的点：

| 待确认 | 用途 |
|---|---|
| 7 个成本口径 | 决定利润是否真实 |
| SKU 加码门槛 | 判断单品是否继续投 |
| 品类复制门槛 | 判断一组 SKU 是否可复制 |
| 平台/国家复制门槛 | 判断进入新平台或新国家 |
| 停止复制门槛 | 防止销售增长但利润亏损 |

## 4. 怎么执行：从业务到 IT 的落地顺序

### 4.1 第一阶段：P0 地基

目标：跑通跨平台复用铺货样板。

| 顺序 | 模块 | 做什么 | 验收重点 |
|---|---|---|---|
| 1 | M10 主数据底座 | 建 P0 表、B1/B2/B3/B4/B7 接口、血缘和版本 | 主数据只能经 B1 写，变更可订阅，ERP 单据单向同步 |
| 2 | M2 Canonical+映射引擎 | 152 键、508 字段映射、枚举字典、必填校验 | 一个 CanonicalProduct 可映射 Amazon/Temu/Shein |
| 3 | M3 6 通用 Skill+执行通道 | SubmitListing 等 6 个操作，API/批量表/RPA 降级 | 操作幂等，结果回写，确定性操作无 LLM |
| 4 | M4 风险分级发布 | 自动/人工/禁发判级 | P0 禁发、P1 人审、确定性操作自动 |
| 5 | M9 多 Agent 编排器 | 任务分解、路由、并发、回滚、上下文共享 | 能编排跨平台复用铺货样板流 |

P0 完成标志：用一个成熟 Listing 抽成 CanonicalProduct，并自动复用发布到另一个或两个平台。

### 4.2 第二阶段：P1 规模化

目标：让系统从能跑样板，变成能批量运营。

| 模块 | 做什么 |
|---|---|
| M1 选品 Priority Score | 情报采集、打分、商品分级、反馈回流 |
| M5 内容生产 | 标题/卖点/描述/图片/质检/人审/表现回流 |
| M6 在线维护 | 库存、价格、广告、滞销等规则触发维护动作 |
| M7 店铺安全风控 | KPI 红线、自动降级、铺货限制、通知 |

### 4.3 第三阶段：P2 经营闭环

目标：用利润和成本决定是否加码、复制或退出。

| 模块 | 做什么 |
|---|---|
| M8 双利润核算 | 边际贡献利润、全成本利润、成本血缘 |
| 广告子 Agent | 广告投放和优化 |
| 客服子 Agent | 售后和异常反馈 |
| 选品权重自动校准 | 用真实销售反馈修正选品打分 |

## 5. 你作为业务负责人需要补齐/确认的事项

这些不是 IT 能凭空决定的，必须由业务、财务、运营一起定。

### 5.1 规则阈值

| 类型 | 需要你定什么 |
|---|---|
| Priority Score | 权重档、S/A/B/C 分箱阈值 |
| 发布风险 | 店铺成熟度门槛、灰度比例、回滚条件 |
| 在线维护 | 库存天数、价格竞争恶化比例、ACOS、滞销周期 |
| 店铺安全 | 各平台 KPI 红线和降级规则 |
| 复制/退出 | SKU、品类、平台、国家复制门槛和停止门槛 |

### 5.2 成本口径

至少要把成本血缘六层定清楚：

1. 战略进入成本。
2. 平台店铺成本。
3. 品牌知识产权成本。
4. 产品准入认证成本。
5. 商品经营成本。
6. 售后风险成本。

否则后面的复制/退出决策会变成“看销售额感觉不错”，而不是看真实利润。

### 5.3 字段和映射数据

| 数据 | 用途 |
|---|---|
| `t_category_mapping` | Canonical 键到平台字段的映射 |
| `t_value_dict` | 枚举值对齐，比如风格、材质、尺码、Shein attr 值 |
| 平台 required 清单 | 决定缺字段时是否阻断发布 |
| 多语言内容 | 标题、描述、卖点等 |

### 5.4 人审边界

你要定清楚哪些必须人审：

| 场景 | 建议 |
|---|---|
| 内容 P0 | 禁止发布，回修 |
| 内容 P1 | 必须人工审核 |
| 新店/低成熟度店铺创造性内容 | 人审或灰度 |
| 不可逆动作 | 人工确认或高等级审批 |
| 确定性维护动作 | 满足规则后自动执行 |

## 7. 当前最大缺口

### 7.1 P0 技术缺口

| 缺口 | 影响 |
|---|---|
| 主数据物理表未齐 | M10 不完成，后面都没有权威源 |
| `t_category_mapping` / `t_value_dict` 未建或未赋值 | M2 映射引擎跑不起来 |
| M9 多 Agent 编排器缺失 | 不能把任务拆给多个 Agent 稳定执行 |
| 执行通道未打通 | M3 Skill 无法真正落到平台 |

### 7.2 业务赋值缺口

| 缺口 | 影响 |
|---|---|
| 55 条左右 draft 规则待赋值 | 规则不能 active，无法自动决策 |
| 7 个成本口径待定义 | 双利润不可算，复制/退出无法自动化 |
| 各平台 KPI 红线待定 | 店铺安全风控不能自动降级 |
| required 字段清单待整理 | 自动刊登会卡在必填校验 |

### 7.3 数据治理风险

| 风险 | 对策 |
|---|---|
| 中台单点错误影响全部自动决策 | 版本、血缘、校验、可观测 |
| ERP 和中台双向打架 | 迁移期坚持单向收敛 |
| LLM 误入确定性操作 | 代码路径硬隔离，不允许 LLM 给价格/库存数值 |
| 平台规则硬编码 | 全部配置化、版本化 |

## 8. 最推荐的下一步动作

### 8.1 开一次业务规则赋值会

参会：业务负责人、运营、财务、技术负责人、PM。

产出：

1. Priority Score 权重和分箱阈值。
2. 在线维护 X/Y/Z/N 阈值。
3. 店铺安全 KPI 红线。
4. 发布成熟度门槛和灰度比例。
5. SKU/品类/平台/国家复制与退出门槛。
6. 成本血缘六层的具体字段和口径。

### 8.2 开一次 P0 技术拆解会

参会：中台、智能平台、刊登/映射、DBA、PM。

议题：

1. M10 表和 B1/B2/B3/B4/B7 接口怎么落。
2. M2 映射引擎输入输出和配置表结构。
3. M3 六个 Skill 的最小平台打通顺序。
4. M4 风险分级如何嵌到发布链路。
5. M9 编排器是否用 LangGraph 式外挂。
6. P0 样板平台组合选哪几个。

### 8.3 选一个最小样板

建议样板：

1. 选择女装类目的一个成熟 Listing。
2. 先抽取 20 个三平台共有 Canonical 键。
3. 优先打通 Amazon → Temu 或 Amazon → Shein 的复用刊登。
4. 跑通字段映射、必填阻断、内容质检、风险判级、执行回写。
5. 再扩展到第三个平台和更多类目。

## 9. 一句话执行总纲
