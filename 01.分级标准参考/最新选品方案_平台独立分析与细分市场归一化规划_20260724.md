# 最新选品总方案：三平台独立分级、细分市场聚类与产品策略拆解

> 版本日期：2026-07-24
>
> 适用平台：Amazon、TikTok、SHEIN
>
> 正式业务方向：`L3 -> L2 -> L1 -> C/B/A/S -> 多平台综合 -> 产品策略拆解`
>
> 文档性质：业务总方案与后续系统重构基线

## 1. 方案结论

新方案不再把不同平台的原始商品数据提前混合，也不再让新品、改款、爆款、长尾作为 L2/L1/S/A 的平行赛道。

Amazon、TikTok、SHEIN 分别运行完整的单平台选品任务。每个平台先在 L3 使用销量等硬性指标筛除没有参考价值的商品；只有 L3 通过商品才进入属性解析和细分市场人工确认。L2、L1 以及最终 C/B/A/S 的评价对象统一改为细分市场。

三大平台分别产出细分市场结果后，系统对平台潜力指标进行标准化，将各平台最优细分市场汇入多平台聚类，并为细分市场生成单平台优势、双平台优势或全平台优势标签。最后再拆解入选细分市场内部的商品，分别判断开发动作和经营类型。

趋势不属于这条自动分级主链。独立品牌站及趋势关键词继续由趋势系统单独处理，业务人员在最终产品判断阶段决定是否叠加趋势元素或进一步研究趋势候选市场。

## 2. 目标与边界

### 2.1 本方案要解决的问题

1. 避免 Amazon、TikTok、SHEIN 原始销量、销售额、排名和内容指标因口径不同而被直接比较。
2. 先在每个平台内部完成可信的商品筛选和细分市场分级。
3. 让细分市场成为 L2 以后稳定的分析和决策对象。
4. 通过统一潜力维度和多平台聚类发现相近机会。
5. 用平台优势标签快速表达一个细分市场更适合哪些平台。
6. 在机会市场确定后，再对其内部商品判断直接上新、改款、爆款型或长尾型等策略。

### 2.2 主流程范围

主流程只处理：

- Amazon；
- TikTok；
- SHEIN。

每个正式任务由以下身份共同确定：

```text
(platform, target_market, category_id, analysis_window)
```

同一平台的不同国家站点、不同一级类目或不同分析窗口均视为不同任务，不能共用未经重新计算的分位、等级或潜力分数。

### 2.3 不进入主流程的内容

- 独立品牌站商品；
- 独立品牌站的商品销量比较；
- 趋势关键词自动改变 L3、L2、L1 或 C/B/A/S；
- 聚类结果自动等同于立项、采购、合规或刊登决定；
- 在平台独立任务完成前读取其他平台结果并影响本平台等级。

独立品牌站完全进入趋势分析体系，不再作为第四个平台进入本方案。

## 3. 总体业务流程

```text
三平台分别采集原始商品数据
-> 平台内身份、证据、去重和数据合法性检查
-> L3 商品级销量及基础指标硬筛
-> 仅对 L3 通过商品提取受控属性
-> 人工确认唯一细分市场
-> 形成平台细分市场快照
-> L2 细分市场初筛
-> L1 细分市场深挖和风险验证
-> 平台内细分市场 C/B/A/S
-> 生成平台内标准化潜力画像
-> 汇总各平台 S/A 细分市场
-> 多平台机会聚类
-> 回填三平台潜力分数并生成平台优势标签
-> 拆解入选机会中的商品
-> 判断开发动作与经营类型
-> 业务人员结合趋势系统作最终决策
```

### 3.1 阶段对象变化

| 阶段 | 主要对象 | 主要动作 | 输出 |
|---|---|---|---|
| 数据入口 | 平台商品记录 | 平台识别、去重、证据和数据合法性检查 | 合法商品观察 |
| L3 | 单个商品 | 按平台销量和基础指标执行硬筛 | `PASS / REJECTED` |
| 细分市场确认 | L3 通过商品 | 属性解析、人工确认唯一细分市场 | 已确认商品归属 |
| L2 | 平台细分市场 | 聚合需求、增长、竞争、价格、内容和风险信号 | 细分市场初评 |
| L1 | L2 入围细分市场 | 定向补采、代表商品抽样、异常和风险验证 | `PASS / PENDING_DATA / REJECTED` |
| 最终分级 | L1 通过细分市场 | 平台内终评 | C/B/A/S |
| 多平台综合 | 各平台 S/A 细分市场 | 标准化、聚类、平台潜力比较 | 机会簇和平台优势标签 |
| 产品策略拆解 | 入选机会内商品 | 判断开发动作、经营类型和证据 | 产品策略候选 |
| 趋势叠加 | 业务人员和趋势证据 | 判断是否增加趋势设计或扩大研究 | 人工最终意见 |

### 3.2 正式层级方向

业务显示层正式采用：

```text
L3 -> L2 -> L1 -> C/B/A/S
```

为避免与旧系统中相反的 L1/L2/L3 命名混淆，代码、数据表和接口使用稳定阶段键：

| 业务显示名 | 稳定阶段键 |
|---|---|
| 数据入口 | `SOURCE_VALIDATION` |
| L3 | `PRODUCT_HARD_SCREEN` |
| 细分市场确认 | `HUMAN_SEGMENT_ASSIGNMENT` |
| L2 | `SEGMENT_INITIAL_SCREEN` |
| L1 | `SEGMENT_DEEP_DIVE` |
| C/B/A/S | `FINAL_SEGMENT_TIER` |
| 多平台综合 | `MULTI_PLATFORM_SYNTHESIS` |
| 产品策略拆解 | `PRODUCT_STRATEGY_EVALUATION` |

任何模块不得只依赖 `L1`、`L2`、`L3` 字样判断业务职责。

## 4. 三个平台的运行隔离

### 4.1 隔离原则

Amazon、TikTok、SHEIN 在产生本平台最终细分市场等级前完全独立运行：

- 使用本平台的数据源和字段口径；
- 使用本平台的 L3 销量及基础指标规则；
- 使用本平台的比较总体和时间窗口；
- 使用本平台的 L2/L1 指标、补采计划和风险规则；
- 独立产生 C/B/A/S；
- 不读取其他平台的分数、等级或聚类结果。

平台间可以共享受控细分市场词表、通用属性定义、证据格式和审计协议，但不能共享未经换算的业务分数。

### 4.2 平台分析重点

| 平台 | 平台内重点信号 |
|---|---|
| Amazon | 销量、销售额、BSR、关键词需求、竞争、价格、评分评论、上架时间、卖家和变体结构 |
| TikTok | 销量、GMV、增长、内容传播、视频或直播带货、达人结构、价格、评价和新鲜度 |
| SHEIN | 销量、排名、上新时间、价格折扣、评价、款式属性、供给密度和生命周期表现 |

实际字段以已验证数据源为准。字段缺失必须保留缺失状态，不允许 LLM 生成看似完整的数值。

## 5. L3：商品级硬筛

### 5.1 L3 的职责

L3 只判断单个商品是否具备进入细分市场分析的基础价值。销量是硬性指标，Amazon、TikTok、SHEIN 均使用各自明确的销量标准。

来源商品无论处于刚上架、成熟还是其他生命周期，都必须满足对应的平台销量规则，不因后续可能被判断为直接上新候选或趋势商品而绕过 L3。

L3 中的 `source_lifecycle_status` 只描述来源商品已经上架多久，用于选择相应的销量硬标准；它不等同于聚类后的 `DIRECT_NEW_LAUNCH` 开发动作。

L3 可以同时使用：

- 销量或平台可验证的等价需求指标；
- 上架时间及与商品生命周期匹配的销量标准；
- 销售额、价格或排名等必要辅助指标；
- 数据完整性、商品有效性和类目相关性；
- 重复、失效、异常或明显无参考价值的判定。

具体阈值不在本总方案中写死，由平台、类目、站点和生命周期共同决定，并以版本化配置发布。

### 5.2 L3 结果处理

| 状态 | 后续处理 |
|---|---|
| `L3_PASS` | 进入属性提取和细分市场人工确认 |
| `L3_REJECTED` | 不做细分市场解析，不进入市场分母，不进入 L2/L1 |

被 L3 淘汰的商品仍保留原始记录、规则版本、关键指标和淘汰原因，用于审计、复盘和阈值校准，但不再消耗 LLM 或人工细分成本。

因此，后续细分市场的商品数量口径必须明确标记为“L3 通过商品数量”，不能将其误称为平台完整市场商品数量。若需要平台全市场规模，应使用平台聚合数据或独立市场容量数据，不从被筛选后的商品池反推。

## 6. 细分市场定义与人工确认

### 6.1 细分市场的作用

细分市场是 L2 以后唯一的主要分级对象。它由可解释的业务属性组合构成，例如：

- 适用人群；
- 使用场景；
- 产品物理特性；
- 功能或需要解决的问题；
- 风格和设计元素；
- 价格带；
- 季节或生命周期属性。

细分市场不是商品标题的自由文本摘要，也不是由模型临时创造且无法复用的标签。

### 6.2 一个商品只属于一个细分市场

取消辅助细分市场。每个 L3 通过商品在同一 taxonomy 版本中只能拥有一个正式 `primary_segment_id`。

人群、场景、领型、材质、风格、价格带等信息作为独立属性标签保存，用于解释、查询和后续聚类，但不会让商品重复计入多个细分市场。

### 6.3 人工是最终确认者

LLM 可以执行以下准备工作：

- 从标题、详情、价格和结构化字段提取受控属性；
- 根据现有 taxonomy 提出细分市场候选；
- 标出低置信度、字段冲突或无匹配项；
- 提供原文证据和选择理由。

LLM 不得直接形成正式细分市场归属。正式归属必须由人工确认：

```text
LLM_ATTRIBUTE_PARSED
-> HUMAN_REVIEW_PENDING
-> HUMAN_APPROVED | HUMAN_REJECTED | TAXONOMY_CHANGE_REQUIRED
```

只有 `HUMAN_APPROVED` 的商品才能进入细分市场快照和 L2。人工可以修改 LLM 候选，也可以在受控流程中提出新市场、合并市场或拆分市场。

### 6.4 Taxonomy 版本

细分市场身份使用：

```text
(taxonomy_version, segment_id)
```

任何新增、合并、拆分或定义调整都生成新版本，并保存旧 ID 到新 ID 的 lineage。历史运行继续引用原版本，不用新定义覆盖旧结论。

同一次多平台综合必须使用同一 taxonomy 版本；三个平台共享词表定义，但每个平台的商品归属分别人工确认。

## 7. 平台细分市场快照

人工确认完成后，每个平台按 `segment_id` 聚合 L3 通过商品，形成不可变的本轮市场快照。

快照至少包含：

- 成员商品及平台证据引用；
- 商品数量和销量、销售额等分布；
- 价格带、评分、评论、上架时间和生命周期分布；
- 核心属性分布；
- 头部集中度和异常商品；
- 代表商品、边界商品和低表现商品；
- 字段覆盖率、样本量和数据置信度；
- 本轮平台、站点、类目和分析窗口。

细分市场快照是 L2、L1、最终等级、标准化和多平台追溯的共同事实基础。

## 8. L2：细分市场初筛

### 8.1 评价对象

L2 主键为：

```text
(run_id, platform, target_market, category_id,
 taxonomy_version, segment_id)
```

主键中不包含 `track_id`。新品、改款、爆款、长尾不在 L2 分流。

### 8.2 L2 评价内容

L2 在平台内部评价细分市场的：

- 需求强度；
- 需求增长和稳定性；
- 竞争强度与进入空间；
- 价格和利润空间；
- 内容传播或搜索承接能力；
- 产品改良空间；
- 商品生命周期结构；
- 样本稳定性和证据置信度；
- 平台特有风险。

L2 输出平台原始分、平台内分位、初评等级、证据、缺口和是否进入 L1。不同平台可以使用不同原始指标和公式，但必须映射到统一的业务维度。

## 9. L1：细分市场深挖

L1 只处理 L2 入围市场，不对所有市场投入相同补采成本。

### 9.1 深挖内容

- 定向补采 L2 缺失的关键数据；
- 检查头部商品是否异常拉高整体表现；
- 抽取头部、中位、低位、新近和问题型代表商品；
- 验证需求是否持续而非单次事件；
- 验证竞争、价格、利润和供应风险；
- 分析评论、内容反馈和可解决问题；
- 检查数据覆盖率、样本量和异常来源；
- 形成可回溯的证据包。

### 9.2 L1 Gate

L1 结果只允许：

```text
PASS
PENDING_DATA
REJECTED
```

只有 `PASS` 可以进入最终 C/B/A/S。`PENDING_DATA` 进入补采队列，不能伪装成较低等级；`REJECTED` 必须记录原因。

## 10. 平台内最终 C/B/A/S

L1 通过后，每个平台独立产生细分市场最终等级。

| 等级 | 业务含义 |
|---|---|
| S | 本平台当前最优、证据充分、优先进入多平台综合 |
| A | 本平台高潜、证据基本完整、进入多平台综合 |
| B | 有一定价值，但优势、证据或风险条件不足 |
| C | 当前不优先，仅保留观察和复盘 |

等级的精确阈值由平台配置决定，但必须遵守：

- 等级只在本平台比较总体内解释；
- 不直接将 Amazon S 与 TikTok S 或 SHEIN S 视为数值相等；
- 每个等级必须绑定平台分数、平台分位、证据和规则版本；
- 单个异常商品不能独自把整个市场推到 S 或 A；
- S/A 是多平台聚类的候选入口，不是最终产品立项结论。

## 11. 多平台综合前的标准化

### 11.1 标准化目的

三平台原始销量、GMV、BSR、排名和内容热度不能直接比较。标准化要把各平台结果映射到统一潜力维度，同时保留原始值和证据。

统一维度包括：

- `demand_strength`；
- `demand_growth`；
- `demand_stability`；
- `competition_opportunity`；
- `price_profit_room`；
- `content_resonance`；
- `product_improvement_room`；
- `freshness_novelty`；
- `risk_control`；
- `evidence_confidence`。

### 11.2 参考总体

每个平台的标准化参考总体为同一平台、目标市场、类目、窗口和 taxonomy 版本下全部可评价的 L2 细分市场，不能只用 S/A 市场计算分位。

每个维度同时保存：

- 平台原始值；
- 平台内分位；
- 统一方向后的标准化值；
- 缺失状态；
- 数据覆盖率；
- 证据置信度；
- 标准化版本和参考总体 ID。

缺失值保持为空并影响置信度，不允许由 LLM 猜测补齐。

### 11.3 平台潜力分数

系统可以基于统一维度形成版本化的 `platform_potential_score`，用于最终平台优势判断。该分数必须：

- 在统一的 0 至 100 或等价标准化空间内表达；
- 可拆解到各统一维度；
- 保留平台内原始分和分位；
- 不使用平台名称作为加分项；
- 不覆盖平台原始 C/B/A/S；
- 在数据不足时输出不可比较状态，而不是虚假低分。

## 12. 多平台最优细分市场聚类

### 12.1 聚类输入

每次正式多平台综合先冻结一个跨平台比较范围：

```text
cross_platform_scope_id =
(amazon_task_run_id, tiktok_task_run_id, shein_task_run_id,
 target_market, unified_category_id, category_mapping_version,
 window_compatibility_version, taxonomy_version,
 normalization_version)
```

只有已经映射到同一目标市场、统一类目、兼容分析窗口和 taxonomy 版本的 Amazon、TikTok、SHEIN 任务才能进入同一轮综合。三个平台对应任务均发布完成后，才允许启动正式聚类和平台优势判断。

跨平台比较范围必须保存三个来源任务、统一类目映射版本和窗口兼容规则。平台任务发布状态只允许：

```text
RUN_COMPLETE         已完成且存在可评价市场
RUN_COMPLETE_EMPTY   已完成且零个可评价 L2 市场
RUN_FAILED           运行失败
RUN_PENDING          尚未完成
```

`RUN_COMPLETE` 表示至少存在一个已经形成 L2 评价的细分市场，即使这些市场最终全部为 B 或 C。`RUN_COMPLETE_EMPTY` 只表示 L3、人工细分和 L2 完成后，没有任何可评价 L2 市场。它是有效观察结果，不等同于数据缺失；只有三个任务均为 `RUN_COMPLETE` 或 `RUN_COMPLETE_EMPTY` 时，比较范围才能从 `DRAFT` 进入 `READY`。

任一平台尚未完成时，系统可以生成标记为 `INCOMPLETE_SCOPE` 的内部诊断结果，但不能发布正式机会簇优先级或平台优势标签。

候选池取三个平台最终 S/A 细分市场的并集。一个候选至少满足：

```text
l1_gate_status = PASS
final_segment_tier in [S, A]
segment_snapshot_status = READY
all_included_members_human_approved = true
normalized_profile_status = READY
taxonomy_version = cross_platform_scope.taxonomy_version
```

聚类成员主键为：

```text
(run_id, platform, target_market, category_id,
 taxonomy_version, segment_id, normalization_version,
 cross_platform_scope_id)
```

主键不包含赛道字段。

### 12.2 聚类含义

聚类根据细分市场的人群、场景、物理特性、风格、价格带和统一机会特征，将相近的最优市场组织成机会簇。

聚在一起表示这些市场具有相近的需求或机会形态，不表示它们是同一商品，也不表示可以忽略平台经营差异。

共享 taxonomy 中完全相同的 `segment_id` 可以直接跨平台对齐；不同 `segment_id` 只有在语义和机会结构相近时才可能进入同一机会簇。

具体聚类方法、距离权重、最小样本和噪声规则由独立版本化配置决定。本总方案固定的是输入、输出、审计和业务边界，不固定算法参数。

### 12.3 聚类输出

每个机会簇至少输出：

- `cluster_id` 和聚类版本；
- 成员细分市场及来源平台；
- 共同人群、场景、物理特性和价格带；
- 共同机会特征与差异特征；
- 各成员标准化画像和证据；
- 各平台成员数量和覆盖状态；
- 代表细分市场和代表商品；
- 聚类稳定度、异常成员和噪声状态；
- 人工确认的机会簇名称和后续动作。

噪声成员不自动淘汰，保留为独立机会并进入人工复核。

### 12.4 机会入选 Gate

聚类完成不等于自动进入商品策略拆解。每个机会簇或独立噪声机会必须形成 `OpportunitySelectionDecision`：

```text
PENDING_REVIEW
APPROVED_FOR_PRODUCT_ANALYSIS
REJECTED
PENDING_DATA
```

进入商品策略拆解至少要求：

- 机会簇或独立噪声机会已经完成人工确认；
- 至少存在一个平台 S/A 成员；
- 平台潜力矩阵已经生成；
- 跨平台分数校准状态允许比较，或明确只作单平台证据分析；
- 不存在阻断性的证据、合规或数据缺口；
- 人工记录入选范围、理由和审批人。

噪声机会可以在人工确认后作为独立机会进入商品分析。聚类回填得到的 B/C 平台商品只进入“比较证据池”，默认不进入产品策略候选池；只有人工明确提升范围后，才可作为产品策略候选。

## 13. 平台潜力比较与优势标签

### 13.1 跨平台细分市场对应关系

相同 taxonomy 版本中的同一 `segment_id` 默认视为同一细分市场，可以直接比较。不同 `segment_id` 被聚到同一机会簇，只代表相关，不自动代表可等价比较。

不同 ID 需要人工维护 `CrossPlatformSegmentMapping`，关系类型只允许：

```text
SAME_MARKET       可作为同一细分市场回填和比较
RELATED_MARKET    只用于聚类解释，不可相互回填分数
PARENT_CHILD      只用于层级解释，不可直接比较
NOT_EQUIVALENT    明确不可比较
```

`SAME_MARKET` 不使用任意两两连线，而是归入一个 `comparison_segment_id` 等价组。一个等价组在同一 `cross_platform_scope_id` 内对每个平台至多包含一个 `segment_id`，最多包含 Amazon、TikTok、SHEIN 三个成员。组成员关系天然对称，不允许通过链式推导自动传递。

映射保存 `comparison_segment_id`、来源平台和 ID、目标平台和 ID、taxonomy 版本、关系类型、证据、审批人、映射版本和 lineage。若同一平台的多个市场被申请加入同一 `SAME_MARKET` 等价组，状态必须为 `MAPPING_CONFLICT`，该等价组不得回填或发布优势标签，直到人工拆分、合并或驳回冲突映射。

只有无冲突的 `SAME_MARKET` 等价组可以用于跨平台潜力回填。

### 13.2 为什么需要回填三个平台

聚类候选池只包含各平台 S/A，但平台优势判断不能只看入池成员。

例如，一个细分市场在 Amazon 为 S，在 TikTok 为 B，在 SHEIN 不存在。如果只看 S/A 候选池，会错误地把另外两个平台当成没有价值或没有数据。因此聚类完成后，系统必须按同一 `segment_id` 或经人工确认的 `SAME_MARKET` 关系，回填三个平台的完整状态。

### 13.3 平台观察状态

每个平台对该细分市场只允许一个观察状态：

```text
HIGH_POTENTIAL
OBSERVED_BUT_NOT_SELECTED
INSUFFICIENT_DATA
NOT_OBSERVED
NOT_APPLICABLE
```

操作定义如下：

| 状态 | 操作含义 |
|---|---|
| `HIGH_POTENTIAL` | 已观察、画像可比较，最终等级为 S 或 A |
| `OBSERVED_BUT_NOT_SELECTED` | 已观察且可评价，但最终未达到 S/A |
| `INSUFFICIENT_DATA` | 已观察，但关键字段或校准条件不足，不能形成可比分数 |
| `NOT_OBSERVED` | 平台任务已完成，但本轮没有该细分市场的有效观察 |
| `NOT_APPLICABLE` | 经业务规则确认该市场不适用于该平台或经营范围 |

只有其他平台存在可比较数据时，才能形成有方向性的“平台优势”结论。

### 13.4 跨平台分数校准 Gate

把三个平台分别缩放到 0 至 100，并不能自动证明分数等值。正式优势判断前必须执行跨平台校准：

1. 统一各维度的业务方向和定义；
2. 使用冻结参考总体生成平台内分位；
3. 使用人工金标市场、历史结果或共同业务锚点校准平台潜力分数；
4. 检查排序一致性、分数区间稳定性、标签稳定性和校准误差；
5. 保存校准样本、指标、版本和验收结果。

校准以“比较范围 + 实际适用平台集合 + 统一维度 schema”为粒度：

```text
calibration_id =
(cross_platform_scope_id, applicable_platform_set,
 normalized_feature_schema_version, calibration_version)
```

`applicable_platform_set` 可以是三平台集合，也可以是在其余平台明确 `NOT_APPLICABLE` 时的两平台集合。每个 `calibration_id` 单独保存锚点样本、维度误差、稳定性结果和状态。

校准状态只允许：

```text
CALIBRATED
CALIBRATION_FAILED
NOT_CALIBRATED
```

只有覆盖当前细分市场实际适用平台集合的 `CALIBRATED` 校准记录，才可以发布正式方向性优势标签。其他状态只能并列展示各平台事实、分位和置信度，不得输出某平台更有优势。

### 13.5 优势标签与证据状态

平台比较先产生独立的证据状态：

```text
COMPLETE_COMPARABLE
PARTIAL_COMPARABLE
SINGLE_PLATFORM_EVIDENCE_ONLY
INSUFFICIENT_CROSS_PLATFORM_DATA
NOT_CALIBRATED
```

`advantage_label` 与 `comparison_evidence_status` 分开保存。证据状态为 `SINGLE_PLATFORM_EVIDENCE_ONLY`、`INSUFFICIENT_CROSS_PLATFORM_DATA` 或 `NOT_CALIBRATED` 时，`advantage_label` 必须为空。

证据状态按以下顺序判定：

| 证据状态 | 操作定义 | 是否允许优势标签 |
|---|---|---|
| `NOT_CALIBRATED` | 跨平台校准未通过 | 否 |
| `INSUFFICIENT_CROSS_PLATFORM_DATA` | 任一应适用平台数据不足或未观察，无法完成必要比较 | 否 |
| `SINGLE_PLATFORM_EVIDENCE_ONLY` | 只有一个平台拥有可比较分数 | 否 |
| `PARTIAL_COMPARABLE` | 至少两个平台可比较，其余平台明确为 `NOT_APPLICABLE` | 可以，但必须标明适用平台范围 |
| `COMPLETE_COMPARABLE` | 三个平台均拥有可比较分数 | 可以 |

正式方向性标签至少包括：

| 标签 | 含义 |
|---|---|
| `AMAZON_ADVANTAGE` | Amazon 潜力明显更强，其他平台有可比较证据 |
| `TIKTOK_ADVANTAGE` | TikTok 潜力明显更强，其他平台有可比较证据 |
| `SHEIN_ADVANTAGE` | SHEIN 潜力明显更强，其他平台有可比较证据 |
| `AMAZON_TIKTOK_ADVANTAGE` | Amazon 与 TikTok 同时具备优势 |
| `AMAZON_SHEIN_ADVANTAGE` | Amazon 与 SHEIN 同时具备优势 |
| `TIKTOK_SHEIN_ADVANTAGE` | TikTok 与 SHEIN 同时具备优势 |
| `ALL_PLATFORM_ADVANTAGE` | 三个平台均达到优势标准 |

优势标签比较的是标准化后的平台潜力，不是原始销量或原始等级。标签必须同时展示三个平台分数、观察状态、置信度和判定版本，不能只显示结论。

对于包含多个相近细分市场的机会簇，先保留每个 `segment_id` 的平台优势标签，再形成簇级摘要；不得用簇平均值覆盖成员差异。

## 14. 聚类后的商品策略拆解

### 14.1 分析时点

旧方案中的新品、改款、爆款、长尾赛道不再参与 L3、L2、L1 或 C/B/A/S 的细分市场分级。来源商品的上架生命周期仍可参与 L3 硬筛；我们的直接上新、改款、爆款型和长尾型判断，只在多平台聚类、平台优势判断和机会入选 Gate 完成后运行。

输入商品必须同时满足：

- L3 通过；
- 细分市场已经人工确认；
- 所属机会的 `OpportunitySelectionDecision` 为 `APPROVED_FOR_PRODUCT_ANALYSIS`；
- 商品属于机会中的 S/A 平台成员，或已被人工明确提升为产品策略候选；
- 商品事实和证据达到最低完整性要求。

### 14.2 两个独立判断维度

为了避免把“怎么开发”和“预期销售形态”混成一个互斥标签，商品策略拆成两个维度。

**开发动作**：

```text
DIRECT_NEW_LAUNCH   直接上新
MODIFICATION        改款开发
NO_ACTION           暂不开发
PENDING_REVIEW      信息不足或需要人工判断
```

**经营类型**：

```text
HIT_POTENTIAL       爆款型
LONG_TAIL           长尾型
NORMAL              常规型
UNCERTAIN           暂不可判断
```

因此，一款商品可以是“改款开发 + 爆款型”，也可以是“直接上新 + 长尾型”。两个维度分别保存分数、证据、规则版本和人工结论。

### 14.3 商品拆解内容

- 核心人群、场景和物理特性；
- 款式、材质、结构、功能和价格；
- 销量、增长、生命周期和平台表现；
- 评论、问题、退货或内容反馈；
- 可直接复用的优势；
- 可改良的问题和具体改款方向；
- 同一机会簇内的相似商品、差异商品和代表商品；
- 所属细分市场的平台优势标签；
- 数据缺口、风险和不适用条件。

这些判断条件可以与旧三赛道不同，由新的商品策略规则单独配置和验证。

## 15. 趋势系统的关系

趋势分析与三平台选品主流程保持独立：

- 独立品牌站完全进入趋势系统；
- 趋势系统持续生成趋势关键词、元素、场景和候选市场；
- 趋势信号不回流修改 L3、L2、L1 或 C/B/A/S；
- 趋势信号不自动把 L3 淘汰商品重新放回主流程；
- 产品策略拆解完成后，业务人员可以结合趋势关键词决定是否增加颜色、图案、材质、结构、内容表达或其他趋势修改；
- 业务人员也可以根据趋势证据发起新的候选细分市场研究，但必须进入下一轮 taxonomy 和人工确认流程。

趋势在本方案中属于最终业务叠加层，而不是自动评分赛道。

## 16. 核心数据对象

### 16.1 `PlatformProductObservation`

保存平台商品原始事实、来源、时间窗口和字段级证据。

```text
(run_id, platform, target_market, product_id)
```

### 16.2 `L3ProductDecision`

保存商品 L3 硬筛结果、关键销量指标、命中规则、规则版本和淘汰原因。

```text
(run_id, platform, target_market, product_id, l3_rule_version)
```

### 16.3 `ProductAttributeProfile`

保存 L3 通过商品的受控属性、LLM 候选、原文证据和置信度，不代表正式细分市场归属。

### 16.4 `SegmentTaxonomy`

保存细分市场定义、属性边界、版本、状态和 lineage。

### 16.5 `ProductSegmentAssignment`

保存商品唯一正式细分市场和人工审批信息。

```text
(run_id, platform, target_market, product_id,
 taxonomy_version, primary_segment_id)
```

每个商品只能有一个有效 `primary_segment_id`，不存在辅助细分市场成员关系。

### 16.6 `PlatformSegmentSnapshot`

保存本轮平台细分市场成员、聚合指标、属性分布、代表商品、样本量和数据覆盖率。

```text
(run_id, platform, target_market, category_id,
 taxonomy_version, segment_id)
```

### 16.7 `PlatformSegmentEvaluation`

保存 L2、L1 和最终 C/B/A/S 结果。主键与快照一致，不包含 `track_id`。

### 16.8 `NormalizedPlatformSegmentProfile`

保存统一维度、平台潜力分数、参考总体、缺失状态、置信度和标准化版本。

### 16.9 `CrossPlatformComparisonScope`

保存 `cross_platform_scope_id`、三个来源任务 ID、统一类目映射版本、窗口兼容规则版本、taxonomy、标准化版本和 `DRAFT / READY / BLOCKED / PUBLISHED` 状态。

### 16.10 `CrossPlatformSegmentMapping`

保存 `comparison_segment_id` 等价组、不同细分市场 ID 的人工对应关系、关系类型、证据、映射版本、审批和 lineage。一个组中每个平台至多一个成员；只有无冲突的 `SAME_MARKET` 关系可以参与分数回填。

### 16.11 `MultiPlatformOpportunityCluster`

保存机会簇、成员快照、聚类版本、代表市场、差异、稳定度和人工结论。

### 16.12 `SegmentPlatformAdvantage`

保存同一细分市场或 `comparison_segment_id` 的三平台潜力矩阵、观察状态、`calibration_id`、校准状态、比较证据状态、优势标签、置信度和判定版本。

### 16.13 `OpportunitySelectionDecision`

保存机会簇或独立噪声机会是否进入商品策略拆解、入选范围、理由、阻断项、审批人和状态。

### 16.14 `ProductStrategyEvaluation`

保存聚类后商品的开发动作、经营类型、依据、风险和人工确认结果。

### 16.15 `TrendBusinessOverlay`

保存业务人员引用的趋势关键词、趋势证据、拟修改元素和最终意见，不反向覆盖主流程历史结果。

## 17. 人工 Gate 与职责

| Gate | 人工职责 | 系统职责 |
|---|---|---|
| 细分市场确认 | 确认唯一市场、处理歧义、发起 taxonomy 变更 | 提供属性、候选和证据 |
| L1 复核 | 判断关键缺口、异常和风险是否可接受 | 提供补采、抽样和证据包 |
| C/B/A/S 发布 | 审批平台最终细分市场结果 | 执行确定性规则并留痕 |
| 聚类确认 | 命名、合并或拆分机会簇 | 提供成员、距离、共同点和差异 |
| 平台优势确认 | 审批优势标签及证据充分性 | 提供三平台潜力矩阵和状态 |
| 机会入选确认 | 决定簇、噪声机会和商品范围是否进入策略拆解 | 提供 Gate、阻断项和候选商品池 |
| 产品策略确认 | 确认直接上新、改款及经营类型 | 提供商品拆解和规则建议 |
| 趋势叠加 | 决定是否采用趋势元素或继续研究 | 提供趋势关键词和证据引用 |

人工修改必须记录修改前结果、修改后结果、原因、操作者和时间，不允许只覆盖原值。

## 18. 版本、状态与审计

正式运行至少冻结：

```text
run_id
platform_rule_version
l3_rule_version
taxonomy_version
segment_scoring_version
normalization_version
clustering_version
segment_mapping_version
category_mapping_version
window_compatibility_version
advantage_label_version
cross_platform_calibration_version
normalized_feature_schema_version
product_strategy_rule_version
analysis_window
reference_population_id
cross_platform_scope_id
```

任一规则、taxonomy、标准化方法或聚类成员变化都产生新版本。已发布结果不原地重算覆盖，而是生成新运行并保留差异。

关键状态必须可追溯：

- 商品为何在 L3 被淘汰；
- 商品由谁确认到哪个细分市场；
- 市场为何进入或未进入 L1；
- 市场为何得到 C/B/A/S；
- 统一潜力维度如何从平台指标得到；
- 机会簇包含哪些成员；
- 哪些不同 ID 被确认成同一市场，哪些只是相关市场；
- 跨平台分数是否通过校准；
- 平台优势标签使用了哪些平台数据；
- 机会为何进入或未进入商品策略拆解；
- 产品为何被判断为直接上新、改款、爆款型或长尾型；
- 趋势元素由谁在何时人工加入。

## 19. 实施阶段规划

### P0：冻结规则和数据契约

交付：

- 三个平台正式任务身份；
- L3 规则配置结构；
- L3/L2/L1/C/B/A/S 稳定阶段键；
- 细分市场 taxonomy 第一版；
- 人工确认流程；
- 核心数据对象和版本字段。

验收：旧系统中的 `track_id` 不再是新主链必要字段；L3、细分市场和后续分级对象没有歧义。

### P1：三平台 L3 商品硬筛

交付：

- Amazon、TikTok、SHEIN 独立 L3 规则；
- `L3_PASS / L3_REJECTED` 结果；
- 淘汰原因和规则版本审计；
- L3 通过商品池。

验收：所有后续商品都满足对应平台的销量硬标准；淘汰商品不进入细分市场处理。

### P2：属性提取和细分市场人工确认

交付：

- 受控属性词表；
- LLM 属性提取和候选输出；
- 人工审批队列；
- 唯一 `primary_segment_id`；
- taxonomy 变更和 lineage 流程。

验收：进入 L2 的每个商品只有一个经人工确认的细分市场，不存在辅助市场和重复计数。

### P3：平台内 L2、L1 和 C/B/A/S

交付：

- 三个平台独立细分市场快照；
- L2 初筛和入围队列；
- L1 补采、代表商品和风险 Gate；
- 平台细分市场 C/B/A/S；
- 完整证据和未入围原因。

验收：每个等级都能追溯到平台事实和成员商品；其他平台数据不会影响本平台等级。

### P4：标准化、多平台聚类和平台优势

交付：

- 统一潜力维度；
- 三平台标准化画像和潜力分数；
- 跨平台比较范围和三平台任务齐套状态；
- 统一类目及窗口兼容映射；
- 跨平台细分市场等价关系；
- 平台集合级分数校准及验收报告；
- S/A 候选池；
- 多平台机会簇；
- 三平台状态回填；
- 单平台、双平台和全平台优势标签。

验收：不直接比较平台原始销量；只有三平台任务齐套且分数校准通过后才发布优势标签；缺少其他平台证据时不会错误生成平台优势结论。

### P5：聚类后产品策略拆解

交付：

- 入选机会内商品池；
- 机会入选 Gate 和审批记录；
- 商品属性、问题和差异拆解；
- 开发动作判断；
- 爆款型、长尾型和常规型判断；
- 人工确认结果。

验收：商品策略在聚类后运行，不反向改变已经发布的细分市场等级。

### P6：趋势业务叠加和试点切换

交付：

- 趋势关键词引用接口或人工引用表；
- 趋势元素人工判断记录；
- 三平台试点报告；
- 新旧流程结果差异和切换方案。

验收：独立品牌站只出现在趋势体系；趋势不能绕过 L3 或自动改写主流程结果。

## 20. 关键验收标准

1. 主流程只包含 Amazon、TikTok、SHEIN。
2. 三个平台在最终 C/B/A/S 产生前完全独立运行。
3. 销量是 L3 硬性指标，来源商品不因刚上架或其他生命周期状态获得例外通道。
4. L3 淘汰商品保留审计，但不划分细分市场、不进入市场分母。
5. 每个 L3 通过商品只有一个人工确认的 `primary_segment_id`。
6. 系统不存在辅助细分市场和重复市场计数。
7. L2、L1、C/B/A/S 的评价对象都是平台细分市场。
8. 新主链的细分市场评价主键不包含 `track_id`。
9. 多平台综合只在各平台独立结果完成后启动。
10. 同一轮综合中的三个任务属于同一目标市场、统一类目、兼容窗口和 taxonomy 版本。
11. 任一平台任务未完成时，不发布正式聚类优先级或平台优势标签。
12. 平台原始销量、GMV、BSR和排名不直接跨平台比较。
13. `RUN_COMPLETE_EMPTY` 只表示零个可评价 L2 市场，不能把 B/C 市场误判为空。
14. 不同 ID 的 `SAME_MARKET` 映射通过每平台至多一个成员的等价组管理，冲突映射不得回填分数。
15. 跨平台分数通过覆盖实际适用平台集合的校准 Gate 后才允许生成方向性优势标签。
16. 平台优势标签能够展示三个平台的分数、状态、置信度和证据。
17. 其他平台无数据时，只标记证据不足，不声称单平台优势。
18. 聚类结果必须经过机会入选 Gate 才能进入商品策略拆解。
19. 旧新品、改款、爆款、长尾赛道只在聚类后转化为商品策略判断。
20. 来源商品生命周期与我们的直接上新动作使用不同字段。
21. 开发动作与经营类型作为两个独立维度保存。
22. 独立品牌站和趋势关键词不进入主分级链。
23. 业务人员可以在最终阶段叠加趋势意见，但不能覆盖历史评分事实。
24. 所有人工修改、规则版本和结果版本均可审计。

## 21. 主要风险与控制

| 风险 | 表现 | 控制方式 |
|---|---|---|
| L3 口径漂移 | 同类商品在不同批次被不同规则筛除 | 平台、类目、生命周期和规则版本冻结 |
| 把筛后商品量当市场总量 | 高估或误解市场规模 | 明确“L3 通过商品口径”，市场总量另取数据 |
| 人工确认成为瓶颈 | 商品等待细分市场审批 | LLM 提供候选、批量审批和冲突优先队列 |
| 细分市场定义不稳定 | 人工在不同批次理解不同 | taxonomy 定义、示例、边界和版本管理 |
| 重复市场计数 | 商品进入多个市场 | 唯一主市场，不设辅助市场 |
| 平台原始指标伪比较 | 销量或排名口径被直接横向使用 | 统一维度、平台内分位和标准化潜力分数 |
| 0 至 100 分数伪等值 | 各平台缩放后看似可比，实际业务含义不同 | 共同锚点、人工金标和跨平台校准 Gate |
| 缺失被误判为低潜力 | 平台没有数据却被标成弱势 | 区分未观察、数据不足和真实低分 |
| 相关市场被当作同一市场 | 同簇不同 ID 被错误回填分数 | 仅 `SAME_MARKET` 映射可比较，其他关系只解释 |
| 聚类掩盖成员差异 | 簇平均值覆盖具体市场 | 成员级标签优先，簇级只做摘要 |
| 聚类后商品范围失控 | B/C 或噪声商品自动进入策略候选 | 机会入选 Gate 和候选池、证据池分离 |
| 商品策略混成单一标签 | 改款和爆款被错误视为互斥 | 开发动作与经营类型分轴 |
| 趋势污染主评分 | 趋势关键词绕过平台硬指标 | 趋势仅在最终人工叠加 |
| 新旧层级接反 | 旧代码按 L1 到 L3 运行 | 稳定阶段键和契约测试 |

## 22. 实施配置项

以下内容不改变主流程，由试点前的版本化配置确定：

- Amazon、TikTok、SHEIN 的 L3 销量及基础指标阈值；
- 不同类目和商品生命周期的销量标准；
- L2 入围、L1 Gate 和 C/B/A/S 阈值；
- 统一潜力维度的计算和权重；
- `platform_potential_score` 的计算方式；
- 统一类目映射和分析窗口兼容规则；
- 跨平台校准样本、误差指标和通过标准；
- 聚类特征、距离、最小样本和噪声处理；
- 单平台、双平台和全平台优势的分数条件；
- 机会入选 Gate 和 B/C 比较证据使用规则；
- 商品开发动作和经营类型的判定条件；
- 各人工 Gate 的岗位、时限和抽检比例。

所有配置必须有版本、适用平台、适用类目、生效时间和审批记录。

## 23. 最终交付形态

系统最终应形成五类业务结果：

1. **平台商品筛选表**：展示 L3 通过、淘汰及原因。
2. **平台细分市场结果表**：展示人工确认成员、L2/L1、C/B/A/S 和证据。
3. **多平台机会簇报告**：展示相近细分市场、共同机会、差异和代表商品。
4. **平台优势判断表**：展示每个细分市场在 Amazon、TikTok、SHEIN 的标准化潜力、状态和优势标签。
5. **商品策略候选表**：展示直接上新、改款、爆款型、长尾型、风险及趋势人工叠加意见。

最终业务人员看到的不是“哪个平台绝对更好”，而是：

- 哪些细分市场已经在单个平台内证明有价值；
- 哪些机会在多个平台具有共同潜力；
- 每个细分市场更偏向哪个平台或哪些平台；
- 机会内部哪些商品适合直接上新或改款；
- 哪些商品更接近爆款型、长尾型或常规型；
- 是否值得结合趋势关键词增加新的设计和研究方向。
