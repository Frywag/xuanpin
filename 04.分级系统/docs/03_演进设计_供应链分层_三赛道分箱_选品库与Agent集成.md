# 演进设计：供应链分层、三赛道分箱、选品库与 Agent 集成

> 本文回应三个流程问题并记录 v0.2 的落地方案：
> ① 供应链字段在初筛期录入不现实，但没有它开款缺依据，怎么办；
> ② 采集字段极多，应从一开始就按三赛道组织采集与评分，在不同评分重点下划分 S/A/B/C；
> ③ 规则写死不够灵活——需要库化的数据结构 + 适配 Claude Code 等 agent CLI，
>    把必要的分析环节交给大模型执行。

---

## 1. 供应链信息：从「逐款录入」改为「三级漏斗」

### 1.1 问题本质

供应链字段（成本/MOQ/交期/面料能力）有两个矛盾属性：

- **对开款决策不可缺**：没有它，S 级推荐只是「市场好」，不是「我们能做」；
- **获取成本极高**：逐款人工核实 2,234 个候选完全不可行。

原 v0.1 的处理（整维缺失、满分从 85 降到 65）诚实但消极——供应链信息
从头到尾不参与排序，开款说服力确实不足。

### 1.2 v0.2 方案：把「一份供应链信息」拆成三级，人力只花在漏斗末端

| 层级 | 信息形态 | 人力成本 | 覆盖范围 | 实现 |
|---|---|---|---|---|
| L1 | **利润结构代理**（零人力）：佣金率、运费/售价比、组内价格位置——全部来自已采集字段 | 0 | 全量 2,234 款（实测 2,169 款拿到代理分） | `scoring.score_supply` ① |
| L1 | **能力档案匹配**（一次性维护）：供应链同事按品类维护 5~20 条能力条目（品类词表、MOQ 区间、交期、成本带），系统词表匹配自动打分 | 一次性 0.5 天，之后零 | 全量 | `configs/supply_capability.yaml` + `score_supply` ② |
| L3 | **逐款人工核实**：target_cost / moq / lead_time 实谈实核 | 每款 0.5~2 天 | 仅 L3 终选款（≤10 款） | `layer_gates_v0.yaml` l3.required_next_data |

关键取舍：

1. 代理指标**永远标注「代理」**且 confidence=medium——它回答「利润结构像不像
   能做的生意」，不冒充毛利事实（红线：不编造毛利）。
2. 能力档案回答「这个品类我们做不做得了」，不回答「这一款成本多少」——
   后者只对终选款人工核实。这样 S 级的语义变成：
   **市场证据多源互验 + 品类能力可覆盖 + 逐款供应链待人工确认**，
   开款依据完整且人力可控。
3. 档案未启用时能力子项记 missing（不打 0 分）——当前仓库没有真实能力数据，
   `supply_capability.yaml` 里是带 `enabled: false` 的示例模板，
   供应链同事填完改 true 即生效，代码零改动。

### 1.3 进一步优化建议（未实现，供决策）

- **反向选品**：能力档案启用后，可以按「能力覆盖的品类 × 市场分数」倒排，
  先看「我们最能做的品类里市场最好的款」，而不是全市场排序后再看能不能做；
- **供应链回流**：终选款人工核实的结果写回 `owned_supply_inputs` 后重跑，
  该款的供应链维变成实测分，历史 run 对比可看到「市场判断 vs 供应链现实」的差距。

## 2. 三赛道：从「事后贴标签」改为「赛道先行、赛道内分箱」

### 2.1 改动

v0.1 用一套权重打完分再贴赛道标签；v0.2 倒过来：

```text
候选包 -> 赛道判定（确定性规则，打分前）
       -> 按赛道权重档打分（weight_profiles，附录C「赛道只调权重」）
       -> 在赛道内部分箱 S/A/B/C（thresholds_by_track）
```

赛道判定规则（优先级从上到下，信号不足时用数据源配置的 `track_hint` 兜底）：

| 赛道 | 判定 | 权重档（需求/竞争/产品/供应链/风险下限） |
|---|---|---|
| 趋势上升款 | 增长率 ≥30%（Tabcut p50=38.9%）或带畅销榜标记 | 30/15/15/20/**-20**（窗口风险放大） |
| 痛点改良款 | 评分 ≤4.30（Shein p25）且评论 ≥10 | 20/15/**30**/20/-15（产品机会优先） |
| 基础常青款 | 基础款词表 + 增长平稳 [-10%,30%) | 22/**28**/15/20/**-10**（竞争结构优先） |
| 均衡（兜底） | 以上都不命中 | 25/20/20/20/-15 |

### 2.2 为什么必须在赛道内分箱（真实数据证明）

本轮实测各赛道 pct 分布：

| 赛道 | n | p50 | p90 | max |
|---|---:|---:|---:|---:|
| trend_rising | 88 | 37.4 | 47.9 | **59.0** |
| pain_improvement | 51 | 42.3 | 45.6 | **46.9** |
| evergreen | 394 | 14.5 | 16.8 | **40.7** |
| balanced | 1,701 | 21.3 | 34.7 | 49.3 |

天花板差 18 分：用全局阈值（S=50）痛点款和常青款**永远出不了头部**，
三赛道就名存实亡。因此 v0.2 的阈值按赛道配置
（`thresholds_by_track`，各约为赛道内前 1% / 5% / 15-50%），实测结果：

| 赛道 | S | A | B | C |
|---|---:|---:|---:|---:|
| trend_rising | 3 | 9 | 50 | 26 |
| pain_improvement | 0 | 12 | 37 | 2 |
| evergreen | 0 | 4 | 12 | 378 |
| balanced | 0 | 17 | 283 | 1,401 |

每个赛道都有自己的头部；S 仍只出现在多源互验候选中（硬性条件不随赛道放松）。

### 2.3 「一开始就突显三赛道采集」

落在两处：

1. `sources_p0.yaml` 每个数据源可声明 `track_hint`（该源按哪个赛道立项采集，
   如图案连裤袜 → evergreen），信号不足的候选按采集意图入赛道；
2. 补采清单按赛道生成含义不同：趋势款优先补「趋势曲线/榜单历史」、
   痛点款优先补「差评全文」、常青款优先补「竞争结构/复购信号」——
   这是下一步采集排期的依据（见推荐总表 next_action 列）。

## 3. 选品库 + Agent CLI + LLM 分析环节

### 3.1 数据结构：SQLite 选品库（`data/selection.db`）

标准库 sqlite3 实现，零新增依赖。设计：**关键字段拉平成列（可 SQL 筛选），
完整对象存 JSON 列（无损）**，每次运行按 run_id 追加，历史可对比：

| 表 | 内容 | 典型查询 |
|---|---|---|
| `runs` | 运行记录、配置快照、等级/赛道分布 | 跨 run 对比阈值调整效果 |
| `envelopes` | SourceEnvelope 头信息 + 完整 JSON | 数据源质量追踪 |
| `candidates` | 候选包：价格/评分/销量/来源数… + 完整 JSON | `WHERE source_group='shein_frontend' AND rating<4.3` |
| `results` | 赛道/等级/pct/各层结果 + 完整 JSON | `WHERE grade IN ('S','A') ORDER BY pct DESC` |
| `evidence` | 证据索引（字段 → 工作簿/sheet/行） | 验收抽查 |
| `llm_analyses` | LLM 回灌结果（human_review=pending） | 人审队列 |

规则不再「写死」的含义：数据在库里、标准在 YAML 里、代码只是引擎——
换标准改 YAML，换数据换库，查数据用 SQL，都不动代码。

### 3.2 Agent CLI 适配

新增子命令（人和 agent 共用，输出均为 JSON）：

```bash
grades                        # 等级×赛道分布
db-query --sql "SELECT ..."   # 只读 SQL（写语句直接拒绝）
show <candidate_id>           # 完整 packet + result
explain <candidate_id>        # 证据链
llm-ingest --bundle .. --output .. --model ..   # 校验并回灌 LLM 结果
```

仓库根新增 `CLAUDE.md`：Claude Code 打开仓库即知道命令、契约、红线。

### 3.3 LLM 分析环节的安全交接（核心设计）

系统**不直接调用 LLM API**，而是生成任务包（`<run>/llm_tasks/*.json`），
由 agent 执行后回灌，本轮实测生成 27 个任务包，三类：

| 任务 | 层级 | LLM 做什么 | LLM 不允许做什么 |
|---|---|---|---|
| review_clustering | L2 | 归纳评价标签为痛点聚类、写改良方向 | 虚构评论内容 |
| cross_platform_compare | L3 | 解读多源互验/价格带/同风格信号，给平台优先级建议 | 凭空找同款、跨币种换算 |
| reason_writer | L3 | 把 AnalysisResult 改写成业务可读语言 | 引入任何新事实 |

任务包结构 = `inputs`（该候选全部可用事实）+ `allowed_evidence_ids`（证据白名单）
+ `output_schema` + `rules`。回灌时 `validate_llm_output` 机器校验：

1. 引用白名单外证据 → 拒绝；
2. 输出中出现输入里不存在的数值（>100 的非平凡数字）→ 拒绝（防编造，
   已实测拦截「月销 58,300 件」这类注入）；
3. 缺 `missing_fields` 声明 → 拒绝；
4. 通过后入 `llm_analyses` 表，`human_review=pending`——**LLM 产出是分析草稿，
   等级与分数永远由确定性引擎决定**，这条边界不随灵活性需求松动。

### 3.4 与 Claude Code 的典型协作流

```text
agent> run 管道                      # 确定性部分：采集->打分->分级->任务包
agent> db-query 找出 S/A 候选        # SQL 直查选品库
agent> 逐个读 llm_tasks/*.json       # 领取分析任务
agent> 生成 JSON 结果 -> llm-ingest  # 机器校验，拒绝则修正重试
人>     人审 llm_analyses 队列 + 终选款供应链核实 -> 立项
```
