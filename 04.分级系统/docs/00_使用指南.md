# 分级系统使用指南

> 面向对象：运行本系统的执行人员（王云涛）、验收的运营、后续接手的同事。
> 看完本文即可独立完成：跑一次分级 → 打开推荐表 → 追溯证据 → 调整标准 → 复跑。
> 分级标准的推导依据见 `01_分级标准_PScoreV0与SABC阈值.md`，
> Gate 与缺失数据规则见 `02_LayerGate规则与缺失数据策略.md`。

## 1. 这个系统做什么

把仓库里已经采好的两类数据源，自动变成一份**带证据链的选品推荐表**：

```text
02.插件数据源/            03.前端数据源/
  Kalodata（女装类目）      Shein 连衣裙 200 款
  Tabcut（Top榜+视频）      独立站（FP/UO/Anthro）
  EchoTik（商品库）         图案连裤袜 7 站 / 万圣节 5 站
        │                        │
        └────────┬───────────────┘
                 ▼
        SourceEnvelope ×7（统一信封）
                 ▼
        CandidateDataPacket ×2,234（多源合并 + 逐字段证据）
                 ▼
        L1 全量粗筛 ──► L2 前40款精调研 ──► L3 前10款多平台比对
                 ▼
        Priority Score + S/A/B/C + 三赛道标签
                 ▼
        选品推荐表.xlsx（8 个 sheet）
```

三个特性务必了解：

1. **全确定性规则**：没有 LLM 参与打分，同样的数据永远得到同样的结果；
2. **证据强绑定**：推荐表里每条理由都能追溯到「哪个工作簿 → 哪个 sheet → 第几行 → 哪个字段」；
3. **缺失即缺失**：没采到的字段显示在 `missing_fields`，绝不会被补成 0 或平均值。

## 3. 跑一次分级（最常用的一条命令）

在**仓库根目录**执行：

```bash
PYTHONPATH="04.分级系统/src" python3 -m grading_system.cli run \
    --repo-root . \
    --out "04.分级系统/data/analysis_runs/run_$(date +%Y%m%d)_001"
```

约 30 秒后输出：

```text
候选总数: 2234
等级分布: {'S': 7, 'A': 48, 'B': 387, 'C': 1792}
L2 处理: 40  L3 处理: 10
产物目录: 04.分级系统/data/analysis_runs/run_20260706_001
```

参数说明（都有默认值，一般只需要改 `--out`）：

| 参数 | 作用 | 默认 |
|---|---|---|
| `--repo-root` | 仓库根目录（数据源路径的基准） | 项目上一级目录 |
| `--out` | 本次运行的产物目录（不存在会自动创建） | 必填 |
| `--sources` | 数据源注册配置 | `configs/sources_p0.yaml` |
| `--scoring` | 分级标准配置 | `configs/scoring_v0.yaml` |
| `--gates` | L1/L2/L3 Gate 配置 | `configs/layer_gates_v0.yaml` |

> 提示：同一个 `--out` 目录可以重复运行（覆盖旧产物）。想对比调参前后差异，
> 用两个不同的 run 目录分别跑。

## 5. 推荐表怎么读（运营视角）

打开 `选品推荐表.xlsx`，**先看第一个 sheet「推荐总表」就够了**，
已按分数从高到低排好，每列都可筛选：

| 列 | 怎么用 |
|---|---|
| `grade` | S/A/B/C 等级。先筛 S 和 A |
| `pct` / `priority_score` | 归一化得分（%）与原始分。同级内比高低 |
| `title` / `category` / `product_link` | 商品是什么、什么类目、页面链接 |
| `track_tags` | 三赛道标签：趋势上升款 / 基础常青款 / 痛点改良款 / 价格带机会款 / 观察款 |
| `recommendation_reason` | 推荐理由（每一条背后都有证据） |
| `risk_summary` | 风险理由（含「人工待确认」标记的，需要人来拍板） |
| `missing_key_fields` | 缺什么数据——**这一列是补采清单的直接来源** |
| `next_action` | 系统建议的下一步 |
| `confidence` | high/medium/low，低置信度的结论要打折看 |
| `L1/L2/L3` | 各层级结果，空 = 未进入该层（成本控制所致，不是漏跑） |

**四个等级的含义与动作**（同任务书定义）：

| 等级 | 含义 | 你该做什么 |
|---|---|---|
| S | 高优先级，值得进立项讨论 | 补齐供应链输入（成本/MOQ/交期）后人审 |
| A | 值得继续研究 | 按 `missing_key_fields` 补数据后复评 |
| B | 暂存观察 | 低成本跟踪价格/榜单/趋势 |
| C | 暂不推进 | 不用管，证据和淘汰理由已留档 |

**怎么追溯一条结论的证据**（验收抽查方法）：

1. 在「推荐总表」看到某条理由，复制该行 `candidate_id`；
2. 切到「证据索引」sheet，按 `candidate_id` 筛选；
3. 每条证据给出 `artifact_path`（哪个工作簿）+ `record_locator`（sheet=xxx;row=N）；
4. 打开对应工作簿的对应行核对原始值——对得上就是真的，对不上算系统 bug。

其余 sheet 的分工：

| Sheet | 内容 | 主要读者 |
|---|---|---|
| 评分明细 | 每个候选 5 个维度的得分、满分、理由、证据 | 想知道「为什么是这个分」的人 |
| 数据源覆盖 | 每个候选来自哪些源、关键字段覆盖率、缺字段 | 安排补采的人 |
| 差评改良 | L2 负面评价聚类：提及次数、改良方向、不改的风险 | 产品开发 |
| 多平台比对 | 多源商品ID互验、同风格价格带（分币种）、红海程度 | L3 终选评审 |
| 风险清单 | 全部风险条目 + 证据，含「人工待确认」项 | 风险复核（蒋锐） |
| 证据索引 | evidence_id → 工作簿/sheet/行/字段 的定位表 | 验收抽查 |
| 运行记录 | run_id、等级分布、运行时统计的价格带分位数 | 复现与审计 |

## 5.5 选品库与 Agent 命令（v0.2 新增）

每次 `run` 会同时把结果写进 SQLite 选品库 `data/selection.db`（跨 run 累积），
并在 `<out>/llm_tasks/` 生成 LLM 分析任务包。常用命令（仓库根目录）：

```bash
# 等级 × 赛道分布
PYTHONPATH="04.分级系统/src" python3 -m grading_system.cli grades

# 只读 SQL 直查（写语句会被拒绝）
PYTHONPATH="04.分级系统/src" python3 -m grading_system.cli db-query \
    --sql "SELECT candidate_id, track, grade, pct FROM results WHERE grade IN ('S','A') ORDER BY pct DESC"

# 单个候选的完整数据包 + 分析结果 / 证据链
PYTHONPATH="04.分级系统/src" python3 -m grading_system.cli show tiktok_shop_1731406217255686451
PYTHONPATH="04.分级系统/src" python3 -m grading_system.cli explain tiktok_shop_1731406217255686451

# 把大模型执行的分析结果校验后回灌（证据白名单 + 数值封闭性校验）
PYTHONPATH="04.分级系统/src" python3 -m grading_system.cli llm-ingest \
    --bundle <out>/llm_tasks/<候选>.review_clustering.json \
    --output <大模型输出.json> --model claude-fable-5
```

LLM 任务包的执行方式和红线见仓库根 `CLAUDE.md` 与 `docs/03` §3.3。
五类任务中 **deep_review（S/高分A 逐款全量评审）** 与 **run_report
（整轮分析报告）** 是正式分析产出：加 `--render` 可渲染成业务可读的
`deep_reviews/<候选>.md` 与 `选品分析报告.md`；评审可在 grade_challenge
中挑战引擎等级，但变更需人审确认。等级与分数的计算始终是确定性的。

## 6. 常见操作

### 6.1 调整分级标准（最常见）

所有标准集中在 `configs/scoring_v0.yaml`，**改配置即改标准，不用动代码**。例如：

```yaml
# 把 S 的门槛从 50 提到 55：
grading:
  thresholds: {S: 55, A: 45, B: 30}

# 把「季节品」扣分从 -3 加重到 -5：
risk:
  rules:
    seasonal_window: {points: -5, desc: 强季节品类，窗口错配即库存风险}
```

改完重跑第 3 节的命令即可。**调完阈值请看新 run 的「运行记录」sheet 里的
等级分布是否还合理**（S 建议保持在前 1% 以内）。

### 6.2 调整 L2/L3 的成本上限

`configs/layer_gates_v0.yaml`：

```yaml
l2:
  max_candidates: 40    # 单次运行最多对多少款做 L2 精调研
l3:
  max_candidates: 10    # 最多对多少款做 L3 多平台比对
```

### 6.3 新增一个前端数据源（不用写代码）

前提：新工作簿沿用前端采集系统的导出格式（每站一个 sheet、中文列名）。
在 `configs/sources_p0.yaml` 的 `frontend_workbooks` 里加一段：

```yaml
  - source_id: zara_frontend            # 唯一 ID
    workbook: 03.前端数据源/zara.xlsx    # 相对仓库根目录
    category_label: women_apparel_zara
    seasonal: false                     # 强季节品类填 true（会触发风险扣分）
    sites: [zara]                       # sheet 名列表
    column_map:                         # 中文列名 → 系统字段
      product_id: 商品ID
      title: 商品名称（原文）
      currency: 币种
      price: 售价
      rating: 评分
      review_count: 评价数
      url: 来源URL
      quality: 质量状态
```

`column_map` 里没有的字段留空即可，系统会自动记入 `missing_fields`。

### 6.4 新增一个插件数据源（需要写一个 Adapter）

参考 `src/grading_system/adapters/kalodata.py`（约 150 行）：
继承 `BaseAdapter`，把工作簿解析成带 `fields` + `evidence` 的 product 记录，
`collect()` 返回 `[SourceEnvelope]`，然后在 `pipeline.py` 的
`PLUGIN_ADAPTERS` 注册、`sources_p0.yaml` 里加一条 `plugin_sources`。

### 6.5 接入供应链人工输入（P1 重点）

当前供应链维（20 分）整体缺失，满分按 65 计。拿到成本/MOQ/交期数据后：

1. 把数据写入候选包的 `owned_supply_inputs`（可做一个 owned 类型的 Adapter）；
2. `scoring_v0.yaml` 里 `supply.enabled: true` 并定义分档；
3. 重跑后满分恢复 85，**必须用新分布重新校准 S/A/B/C 阈值**
   （方法：看运行记录 sheet 的 pct 分位数，按 S≈前0.5%、A≈前2%、B≈前20% 重设）。

### 6.6 补采了评论全文之后

L2 目前用 Shein 页面的「评价标签+次数」做确定性聚类。拿到差评全文后，
扩展 `review_tags.py` 的输入即可；负面词表在 `NEGATIVE_TAG_MAP`，
新增词条时**只加实采中真实出现过的标签**，不要凭空造词。

## 8. 常见问题（FAQ）

**Q：为什么图案连裤袜/万圣节几乎全是 C？**
这两组数据没有采到任何需求信号（销量/GMV/收藏/畅销榜），L1 Gate 规定
「无需求信号 → 强制 C + 补采清单」。这是数据缺失的正确表达，不是品类被判死刑；
按「数据源覆盖」sheet 的缺字段补采后重跑会自动重排。

**Q：为什么 OEAK 文胸双源互验、置信度 high，却只有 A 不是 S？**
它命中 `seller_type=BRAND`（品牌自营）侵权风险，规则规定未确认的重大 IP
风险封顶 A。人工确认风险可控后，可在复评时解除。

**Q：供应链数据不是没有吗，为什么供应链维有分数？**
v0.2 起供应链维两级化：佣金率、运费/售价比、组内价格位置这三个**利润结构
代理指标**零人力可得（理由里都带「代理」字样，不是毛利事实）；品类级能力
档案（`configs/supply_capability.yaml`）由供应链同事一次性维护后启用；
逐款成本/MOQ/交期人工核实只对 L3 终选款（≤10 款）触发。详见 docs/03 §1。

**Q：同样的分数，为什么不同赛道等级不一样？**
S/A/B/C 在**赛道内部**分箱（趋势上升/痛点改良/基础常青/均衡四档权重和阈值
都不同）。各赛道天花板差异很大（实测趋势款 max=59、常青款 max=40.7），
全局阈值会让低天花板赛道永远没有头部。详见 docs/03 §2。

**Q：为什么有的候选 L2/L3 列是空的？**
成本控制：L2 只处理 L1 入围的前 40 款，L3 只处理 L2 后 S/A 的前 10 款。
空 = 没轮到，不是出错。想扩大范围改 `layer_gates_v0.yaml` 的上限。

**Q：Kalodata 是人民币、其他源是美元，分数怎么可比？**
系统从不跨币种换算（汇率不是采集事实）。价格类打分用「组内分位位置」
（各来源和自己组比），多平台比对时各报各币种并注明。

**Q：报 `ModuleNotFoundError: No module named 'grading_system'`？**
命令前面漏了 `PYTHONPATH="04.分级系统/src"`，或者不在仓库根目录执行。

**Q：报 `FileNotFoundError: 02.插件数据源/...`？**
`--repo-root` 没指到仓库根目录。在仓库根目录执行并传 `--repo-root .`。

**Q：想只跑某一类数据源？**
复制一份 `sources_p0.yaml`，删掉不要的条目，用 `--sources` 指向它。

## 9. 术语速查

| 术语 | 含义 |
|---|---|
| SourceEnvelope | 数据源统一信封：一个数据源一次交付的全部记录 + 质量状态 + 产物路径 |
| CandidateDataPacket | 候选数据包：一个商品的全部事实 + 证据 + 缺字段清单，分析的唯一输入 |
| EvidenceRef | 字段级证据：定位到工作簿/sheet/行/字段 |
| Priority Score (PScore) | 需求25 + 竞争20 + 产品机会20 + 供应链20 − 风险15 的总分 |
| pct | PScore ÷ 当前可得满分 × 100（P0 可得满分 = 65） |
| L1/L2/L3 | 全量粗筛 / 入围精调研 / 终选多平台比对 |
| Gate | 层与层之间的准入规则 + 成本上限 |
| track_tags | 三赛道标签（趋势上升/基础常青/痛点改良/价格带机会/观察） |
| missing_fields | 缺失字段清单，同时是补采任务清单 |
| 人工待确认 | 系统只负责标记、必须由人拍板的风险项（如侵权） |
